## Pourquoi ce module ?

Django est l'un des frameworks web les plus utilisés au monde. Il permet de construire
rapidement des applications solides, sécurisées et maintenables avec Python. Pourtant,
les débutants se perdent souvent dans la documentation officielle, très complète mais
peu progressive. Ce module a été écrit pour combler cet écart.

Nous avons choisi un fil rouge unique : une petite application de gestion de
bibliothèque appelée GesiBiblio. Chaque chapitre ajoute une brique à cette
application. À la fin, vous ne disposez pas seulement de notes de cours : vous avez
un projet fonctionnel, que vous pouvez montrer, expliquer et faire évoluer.



## À qui s'adresse ce module ?

Ce module est destiné aux personnes qui débutent en développement web et qui
souhaitent apprendre Django par la pratique. Il ne suppose aucune connaissance
préalable de Django. En revanche, une familiarité minimale avec Python, le terminal
et le HTML est un vrai atout. Les rappels nécessaires sont fournis au fil des
chapitres et dans les annexes.


OBJECTIFS DU CHAPITRE

À la fin de ce module, vous serez capable de :

  - installer Python, créer un environnement virtuel et installer Django ;
  - expliquer le rôle de chaque fichier d'un projet Django ;
  - créer une application, des vues, des URL et des gabarits ;
  - concevoir des modèles de données et maîtriser les migrations ;
  - interroger la base avec l'ORM de Django ;
  - gérer les requêtes HTTP, les formulaires et les fichiers envoyés ;
  - utiliser l'administration Django et personnaliser son affichage ;
  - mettre en place l'authentification, les groupes et les permissions ;
  - appliquer les bonnes pratiques de structuration et de sécurité.

## Qu'est-ce que Django ?

Django est un framework web écrit en Python. Un framework est une boîte à
outils complète : il fournit une structure de projet, un routeur d'URL, un moteur de
gabarits, une couche d'accès à la base de données, une administration automatique,
un système d'authentification et de nombreuses protections contre les failles
courantes.

Sans framework, il faudrait écrire soi-même tout cela : lire les requêtes HTTP,
analyser les formulaires, se connecter à la base, échapper le HTML, gérer les
sessions, hacher les mots de passe, etc. Django s'occupe de ces tâches répétitives
et vous laisse vous concentrer sur ce qui est propre à votre application.


[A RETENIR]

Django suit une philosophie simple : « ne vous répétez pas » (DRY, pour
Don't Repeat Yourself) et « tout est inclus » (batteries included).
Le framework privilégie les conventions claires et la sécurité par défaut.

[/A RETENIR]

Django est utilisé par des sites de toutes tailles : des journaux en ligne, des
plateformes d'enseignement, des applications de gestion, des API mobiles. Sa
documentation est excellente et sa communauté très active. C'est donc un excellent
premier framework pour apprendre le développement web professionnel.



## Comment fonctionne une application web

Une application web repose sur un dialogue entre un client et un
serveur. Le client est le plus souvent un navigateur : Chrome, Firefox,
Safari ou Edge. Le serveur est un programme qui écoute sur un port et répond aux
demandes.

Le dialogue utilise le protocole HTTP. Une requête contient :

  - une méthode : `GET` pour demander une page, `POST` pour envoyer
    des données ;
  - une URL : par exemple `/livres/le-petit-prince/` ;
  - des en-têtes : le navigateur, la langue, les cookies, etc. ;
  - parfois un corps : les champs d'un formulaire ou un fichier.

Le serveur renvoie une réponse avec un code de statut, des en-têtes et un
corps. Les codes les plus courants sont `200` (succès), `301` ou
`302` (redirection), `404` (page introuvable) et `500` (erreur du
serveur).


[NOTE]

Quand vous tapez une adresse dans un navigateur, vous envoyez une requête
`GET`. Quand vous validez un formulaire de connexion, vous envoyez une requête
`POST`. Cette distinction est fondamentale : on ne modifie jamais une donnée
avec une requête `GET`.

[/NOTE]



## Le modèle MVT de Django

Django organise le code selon trois responsabilités : le modèle, la
vue et le gabarit. C'est le modèle MVT, pour
Model, View, Template.


[FIGURE] Le trajet d'une requête dans Django. La vue orchestre le modèle et le gabarit, puis renvoie une réponse HTTP.



  - Le modèle : Il décrit les données et les règles métier. Un modèle Django est
    une classe Python qui correspond à une table de la base de données. Par exemple,
    `Livre` contient un titre, un ISBN, un auteur et un nombre d'exemplaires.
  - La vue : C'est une fonction ou une classe Python qui reçoit une requête,
    récupère les données nécessaires, choisit un gabarit et renvoie une réponse. La
    vue contient la logique de la page.
  - Le gabarit : C'est un fichier HTML enrichi de balises Django. Il affiche les
    données préparées par la vue. Le gabarit ne doit pas contenir de logique métier.


[ATTENTION]

Le vocabulaire de Django peut surprendre si vous venez du modèle MVC classique.
Dans Django, la « vue » joue le rôle du contrôleur, et le « gabarit »
joue le rôle de la vue. Le tableau suivant clarifie la correspondance.

[/ATTENTION]


Django (MVT) | MVC classique | Rôle
Modèle | Modèle | Données, relations, règles métier
Vue | Contrôleur | Reçoit la requête, prépare les données, choisit la réponse
Gabarit | Vue | Présentation HTML, affichage des données

Tableau : Correspondance entre MVT et MVC.

Le trajet complet d'une requête est le suivant :

  1. le navigateur envoie une requête vers une URL ;
  2. le routeur (`urls.py`) associe l'URL à une vue ;
  3. la vue interroge les modèles si nécessaire ;
  4. la vue transmet les données au gabarit ;
  5. le gabarit produit le HTML ;
  6. la vue renvoie une réponse HTTP au navigateur.



## Le projet fil rouge : GesiBiblio

Tout au long du module, vous développez GesiBiblio, une application de gestion de
bibliothèque. Le scénario est simple : une petite bibliothèque veut remplacer son
cahier par un site web. Les lecteurs consultent le catalogue et voient leurs
emprunts. Les bibliothécaires ajoutent des livres, enregistrent les prêts et les
retours.


Fonctionnalité | Description
Catalogue | Liste des livres avec recherche par titre, auteur ou ISBN.
Fiche livre | Détail d'un livre : auteur, catégories, résumé, couverture.
Gestion des livres | Ajout, modification et suppression par les bibliothécaires.
Emprunts | Enregistrement d'un prêt, date de retour prévue, retour et retard.
Comptes | Inscription, connexion, déconnexion et espace personnel.
Permissions | Un lecteur consulte, un bibliothécaire gère le catalogue.
Administration | Interface Django pour gérer toutes les données.
Design | Interface responsive, lisible sur ordinateur et sur téléphone.

Tableau : Fonctionnalités de l'application GesiBiblio.

Les données principales sont les suivantes :

  - Auteur : prénom, nom, biographie, date de naissance ;
  - Catégorie : nom, slug, description ;
  - Livre : titre, ISBN, auteur, catégories, éditeur, année,
    exemplaires, couverture, statut ;
  - Membre : utilisateur Django, numéro de carte, téléphone, adresse ;
  - Emprunt : livre, membre, date d'emprunt, date de retour prévue,
    date de retour effective.

Le projet est volontairement petit. Un bon projet de formation n'est pas un projet
gigantesque : c'est un projet que vous comprenez entièrement, que vous pouvez

[/BONNE PRATIQUE]



## Préparer l'environnement de travail

Avant d'installer Django, vérifiez que Python est disponible. Ouvrez un terminal
(PowerShell sous Windows, Terminal sous macOS ou Linux) et tapez :


TERMINAL :
  $ python --version

Vous devez obtenir une version 3.10 ou supérieure, par exemple :


TERMINAL :
  $ Python 3.12.7


[ATTENTION]

Sous Windows, si la commande `python` ouvre le Microsoft Store au lieu
d'afficher une version, Python n'est pas installé ou n'est pas dans le
`PATH`. Réinstallez Python depuis python.org en cochant « Add Python to PATH
», puis rouvrez le terminal. Vous pouvez aussi essayer la commande `py`.

[/ATTENTION]



### Créer un dossier de travail

Créez un dossier pour la formation, puis placez-vous dedans. Par exemple :


TERMINAL :
  $ mkdir gesibiblio
  $ cd gesibiblio

Tout le projet vivra dans ce dossier. Évitez les chemins contenant des caractères
exotiques ou des espaces, surtout sous Windows. Un chemin simple comme
{C:projetsgesibiblio} évite bien des surprises.



### Créer un environnement virtuel

Un environnement virtuel isole les dépendances du projet. Les paquets installés
pour GesiBiblio ne pollueront pas le Python global de votre machine.


TERMINAL :
  $ python -m venv .venv

Activez ensuite l'environnement. Sous Windows :


TERMINAL :
  $ .venv\Scripts\activate

Sous macOS ou Linux :


TERMINAL :
  $ source .venv/bin/activate

Le prompt du terminal commence maintenant par `(.venv)`. C'est le signe que
l'environnement est actif.


[ATTENTION]

L'activation ne dure que le temps de la session du terminal. Si vous fermez le
terminal, il faut réactiver l'environnement avant de lancer le serveur ou
d'installer un paquet. Si la commande `python` ne trouve plus Django, c'est
souvent que l'environnement n'est pas activé.

[/ATTENTION]



### Installer Django et Pillow

Mettez pip à jour, puis installez Django et Pillow. Pillow est la bibliothèque
d'images utilisée par Django pour les champs `ImageField`.


TERMINAL :
  $ python -m pip install --upgrade pip
  $ python -m pip install "Django>=5.2,<6.0" Pillow


[NOTE]

Les guillemets autour de `"Django>=5.2,<6.0"` sont importants dans un
terminal : ils empêchent le shell d'interpréter les caractères `>` et
`<` comme des redirections. Sous Windows, PowerShell peut aussi avoir besoin
des guillemets.

[/NOTE]



### Vérifier l'installation


TERMINAL :
  $ python -m django --version

La réponse ressemble à `5.2.7`. Le numéro exact dépend du moment de votre
installation. L'important est que la commande affiche une version 5.2.x.

Vous pouvez aussi lister les paquets installés :


TERMINAL :
  $ python -m pip list

Vous devez y voir `Django` et `Pillow`.

## Le rôle de chaque fichier


Fichier ou dossier | Rôle | À modifier ?
`manage.py` | Point d'entrée des commandes du projet. Il appelle
`django-admin` avec le bon fichier de réglages. | Rarement
`gesibiblio/__init__.py` | Indique que le dossier est un paquet Python.
Il reste vide. | Non
`gesibiblio/settings.py` | Configuration complète : applications, base de

`gesibiblio/urls.py` | Table de routage racine. Elle associe les URL aux vues

`gesibiblio/asgi.py` | Point d'entrée ASGI, pour les serveurs asynchrones.

`gesibiblio/wsgi.py` | Point d'entrée WSGI, pour les serveurs synchrones

`db.sqlite3` | Base de données SQLite créée par les migrations. | Non, généré
`migrations/` | Historique des modifications du schéma de base. | Non, généré
`__pycache__/` | Cache des fichiers Python compilés. | Non, généré

### manage.py

`manage.py` est le couteau suisse du projet. Il permet de lancer le serveur,
de créer les migrations, de les appliquer, d'ouvrir un shell Python, de créer un
superutilisateur, etc.


------------------------------------------------------------------------------
CODE : manage.py
------------------------------------------------------------------------------
#!/usr/bin/env python
"""Django's command-line utility for administrative tasks."""
import os
import sys


def main():
    """Run administrative tasks."""

### wsgi.py et asgi.py

Ces deux fichiers exposent l'application Django à un serveur web. Ils ne se
modifient presque jamais.


------------------------------------------------------------------------------
CODE : gesibiblio/wsgi.py
------------------------------------------------------------------------------

[/NOTE]

### Les variables d'environnement

La clé secrète et le mode debug ne doivent pas être codés en dur dans un dépôt
public. On utilise des variables d'environnement. Créez un fichier
`.env.example` qui montre les variables attendues, sans les vraies valeurs :


------------------------------------------------------------------------------
CODE : .env.example
------------------------------------------------------------------------------
DJANGO_SECRET_KEY=changez-moi
DJANGO_DEBUG=True
DJANGO_ALLOWED_HOSTS=127.0.0.1,localhost
------------------------------------------------------------------------------

Puis, dans `settings.py`, lisez ces variables avec le module `os` :


------------------------------------------------------------------------------
CODE : gesibiblio/settings.py, extrait
------------------------------------------------------------------------------
import os
from pathlib import Path

BASE_DIR = Path(__file__).resolve().parent.parent

SECRET_KEY = os.environ.get(
    "DJANGO_SECRET_KEY",
    "django-insecure-cle-de-developpement-uniquement",
)
DEBUG = os.environ.get("DJANGO_DEBUG", "True") == "True"
ALLOWED_HOSTS = os.environ.get(
    "DJANGO_ALLOWED_HOSTS",
    "127.0.0.1,localhost",
).split(",")
------------------------------------------------------------------------------


[ATTENTION]

Le fichier `.env` contient les vraies valeurs et ne doit jamais être
versionné. Le fichier `.env.example` peut l'être : il sert de modèle. Ajoutez
`.env` à `.gitignore`.

[/ATTENTION]


[BONNE PRATIQUE]

Pour charger automatiquement le fichier `.env` en développement, vous pouvez
installer `python-dotenv` et ajouter ces deux lignes au début de
`settings.py` :

------------------------------------------------------------------------------
CODE : gesibiblio/settings.py, extrait
------------------------------------------------------------------------------

load_dotenv(BASE_DIR / ".env")
------------------------------------------------------------------------------

Pour un projet de formation, les variables d'environnement du système suffisent.
En production, le serveur ou la plateforme d'hébergement fournit ces variables.

[/BONNE PRATIQUE]

==============================================================================
CHAPITRE 3 : CRÉER UNE APPLICATION DJANGO
==============================================================================


Un projet Django est composé d'applications. Dans ce chapitre, vous créez l'application `catalogue`, vous découvrez le rôle de ses fichiers et vous affichez votre première page web. Vous comprenez aussi comment une URL est associée à une vue et comment Django renvoie une réponse au navigateur.


OBJECTIFS DU CHAPITRE


  - Distinguer un projet Django d'une application Django.
  - Créer une application avec `startapp`.
  - Enregistrer l'application dans `INSTALLED_APPS`.
  - Écrire une première vue et la relier à une URL.
  - Utiliser `include`, `app_name` et les noms d'URL.
  - Tester le résultat dans le navigateur.



## Projet et application : quelle différence ?

Un projet est l'ensemble du site : sa configuration, ses réglages, ses
URL racines. Une application est un module qui remplit une responsabilité
précise : catalogue, comptes, emprunts, paiements, blog, etc.


[A RETENIR]

Un projet contient plusieurs applications. Une application peut être réutilisée
dans plusieurs projets. Le projet GesiBiblio contiendra au minimum une
application `catalogue`, chargée des livres, des auteurs, des catégories et
des emprunts. Les comptes utilisateurs s'appuieront sur l'application
`django.contrib.auth` fournie par Django.

[/A RETENIR]

Au début, il est tentant de tout mettre dans une seule application géante. C'est
une mauvaise habitude. Une application doit rester cohérente : si vous devez
expliquer son rôle en une phrase, c'est bon signe. `catalogue` gère le
catalogue et les prêts. Plus tard, vous pourriez ajouter `blog`,
`facturation` ou `notifications` sans toucher au catalogue.



## Créer l'application catalogue

Placez-vous dans le dossier qui contient `manage.py`, activez
l'environnement virtuel, puis lancez :


TERMINAL :
  $ python manage.py startapp catalogue

Django crée le dossier `catalogue/` avec les fichiers suivants :


------------------------------------------------------------------------------
CODE : Arborescence de l'application
------------------------------------------------------------------------------
catalogue/
|-- __init__.py
|-- admin.py
|-- apps.py
|-- migrations/
|   `-- __init__.py
|-- models.py
|-- tests.py

[NOTE]

`startapp` ne crée pas de fichier `urls.py`. C'est volontaire : toutes

## Le rôle de chaque fichier de l'application


Fichier | Rôle
`__init__.py` | Transforme le dossier en paquet Python. Il reste vide.
`admin.py` | Enregistre les modèles dans l'interface d'administration.
`apps.py` | Configuration de l'application : nom, libellé, éventuels
branchements au démarrage.
`models.py` | Définit les modèles de données, c'est-à-dire les tables et
leurs relations.
`views.py` | Contient les vues, les fonctions qui reçoivent les requêtes et
renvoient les réponses.
`tests.py` | Contient les tests automatisés de l'application.
`migrations/` | Historique des modifications du schéma de base de données.
`urls.py` | À créer : table de routage propre à l'application.

Tableau : Rôle des fichiers d'une application Django.



### apps.py

------------------------------------------------------------------------------

    default_auto_field = "django.db.models.BigAutoField"

## Enregistrer l'application

Une application n'est active que si elle figure dans la liste des applications
installées. Ouvrez le fichier de réglages du projet et ajoutez la ligne suivante
à la fin de cette liste :


------------------------------------------------------------------------------
CODE : gesibiblio/settings.py, extrait
------------------------------------------------------------------------------
INSTALLED_APPS = [
    "django.contrib.admin",
    "django.contrib.auth",
    "django.contrib.contenttypes",
    "django.contrib.sessions",
    "django.contrib.messages",
    "django.contrib.staticfiles",
    "catalogue.apps.CatalogueConfig",
]
------------------------------------------------------------------------------

Vous pouvez aussi écrire simplement `"catalogue"`. Django retrouvera la
classe `CatalogueConfig` grâce à la convention de nommage. La forme complète
est plus explicite et permet de personnaliser le libellé.


[ATTENTION]

Si vous oubliez d'enregistrer l'application, Django ne verra ni ses modèles, ni
ses gabarits, ni ses fichiers statiques. Les erreurs du type {No installed
app with label 'catalogue'} viennent presque toujours de là.

[/ATTENTION]



## Première vue

Une vue est une fonction Python qui reçoit un objet `request` et renvoie un
objet `response`. Pour commencer simplement, nous allons renvoyer du HTML
brut avec `HttpResponse`.


------------------------------------------------------------------------------
CODE : catalogue/views.py
------------------------------------------------------------------------------
from django.http import HttpResponse


def accueil(request):
    return HttpResponse(
        "<h1>Bienvenue dans GesiBiblio</h1>"
        "<p>La bibliothèque ouvre bientôt ses portes.</p>"
    )
------------------------------------------------------------------------------


  - `request` : Représente la requête HTTP. Il contient la méthode, l'URL,
    les paramètres, l'utilisateur connecté, les cookies, etc. Même si nous ne
    l'utilisons pas encore, il doit toujours être présent dans la signature.
  - `HttpResponse` : Représente la réponse HTTP. Le premier argument est
    le corps de la réponse, ici une chaîne HTML. Django ajoute automatiquement les
    en-têtes et le code de statut `200`.


[NOTE]

Écrire du HTML dans une vue est utile pour comprendre le mécanisme, mais ce n'est
pas une bonne pratique. Dès le chapitre suivant, nous utiliserons des gabarits
pour séparer la présentation de la logique.

[/NOTE]



## Relier une URL à la vue

Créez le fichier `catalogue/urls.py` :


------------------------------------------------------------------------------
CODE : catalogue/urls.py
------------------------------------------------------------------------------
from django.urls import path
from . import views

app_name = "catalogue"

urlpatterns = [
    path("", views.accueil, name="accueil"),
]
------------------------------------------------------------------------------

Puis modifiez le fichier `gesibiblio/urls.py` pour inclure ces URL :


------------------------------------------------------------------------------
CODE : gesibiblio/urls.py
------------------------------------------------------------------------------
from django.contrib import admin
from django.urls import include, path

urlpatterns = [
    path("admin/", admin.site.urls),
    path("", include("catalogue.urls")),
]
------------------------------------------------------------------------------



### Comprendre path et include


  - `path("", vue, name="...")` : Associe une URL à une vue. Ici, la
    chaîne vide correspond à la racine du site. Le nom `accueil` permet de
    construire l'URL dans les gabarits et dans le code Python.
  - `include("catalogue.urls")` : Délègue le routage à l'application. Toute
    URL non consommée par les routes précédentes est cherchée dans
    `catalogue/urls.py`. C'est ce qui rend les applications autonomes.
  - `app_name = "catalogue"` : Crée un espace de noms. Le nom complet de
    la route devient `catalogue:accueil`. Deux applications peuvent ainsi avoir
    une route `accueil` sans se marcher dessus.


[BONNE PRATIQUE]

Nommez toujours vos routes. Une URL codée en dur dans un gabarit casse dès que le
chemin change. |{
et signale les erreurs à la compilation des gabarits.

[/BONNE PRATIQUE]

## Ajouter une deuxième page

Pour voir la mécanique en action, ajoutons une page « À propos ».


------------------------------------------------------------------------------
CODE : catalogue/views.py
------------------------------------------------------------------------------

    return HttpResponse(
        "<h1>Bienvenue dans GesiBiblio</h1>"
        "<p>La bibliothèque ouvre bientôt ses portes.</p>"
    )


def a_propos(request):
    return HttpResponse(
        "<h1>À propos de GesiBiblio</h1>"
        "<p>Un projet de bibliothèque réalisé avec Django.</p>"
    )
------------------------------------------------------------------------------


------------------------------------------------------------------------------
CODE : catalogue/urls.py
------------------------------------------------------------------------------
from django.urls import path
from . import views

app_name = "catalogue"

urlpatterns = [
    path("", views.accueil, name="accueil"),
    path("a-propos/", views.a_propos, name="a_propos"),
]
------------------------------------------------------------------------------

Visitez `http://127.0.0.1:8000/a-propos/`. La page s'affiche.


[NOTE]

L'URL se termine par une barre oblique. Django peut ajouter automatiquement cette
barre grâce au réglage `APPEND_SLASH`, activé par défaut. Prenez l'habitude
d'écrire des URL cohérentes, avec une barre finale.

[/NOTE]



## Le cycle requête réponse

Voici ce qui se passe lorsque vous demandez `/a-propos/` :


# | Composant | Action
1 | Navigateur | Envoie une requête `GET /a-propos/`.
2 | Middlewares | Ajoutent la session, l'utilisateur, la protection CSRF.
3 | `gesibiblio/urls.py` | Ne reconnaît pas `admin/`, délègue à
`catalogue.urls`.
4 | `catalogue/urls.py` | Reconnaît `a-propos/` et appelle
`a_propos`.
5 | Vue | Reçoit `request`, prépare la réponse.
6 | `HttpResponse` | Renvoie le HTML avec le statut `200`.
7 | Navigateur | Affiche le corps de la réponse.

Tableau : Trajet d'une requête vers la page « À propos ».


[A RETENIR]

Une URL n'est pas un fichier. C'est une route décrite dans `urls.py`. Le
serveur ne cherche pas `a-propos.html` sur le disque : il appelle la fonction
`a_propos`, qui construit la réponse.

[/A RETENIR]



## Bonnes pratiques


[BONNE PRATIQUE]


  - Une application, une responsabilité claire.
  - Un fichier `urls.py` par application, inclus depuis le routeur racine.
  - Un `app_name` et des noms de routes explicites.
  - Des URL en minuscules, avec des tirets, et une barre finale.
  - Des vues courtes : la logique métier lourde va dans les modèles, les
    formulaires ou des services dédiés.
  - Pas de HTML dans les vues : utilisez des gabarits dès que possible.


[/BONNE PRATIQUE]


[ERREUR FREQUENTE]

Deux erreurs classiques débutent par la même confusion : `include` ne
fonctionne que si le module cible expose une variable `urlpatterns`, et
`app_name` doit être identique au préfixe utilisé dans
|{
ailleurs.

[/ERREUR FREQUENTE]

==============================================================================
CHAPITRE 4 : CHARGER ET ORGANISER LES GABARITS
==============================================================================


Un site web sans HTML n'affiche rien. Dans ce chapitre, vous découvrez le moteur de gabarits de Django, la fonction `render`, l'héritage avec `base.html` et les inclusions. Vous transformez la page d'accueil en un vrai gabarit, prêt à recevoir le design du chapitre suivant.


OBJECTIFS DU CHAPITRE


  - Configurer le moteur de gabarits dans `settings.py`.
  - Afficher un gabarit avec `render` et un dictionnaire de contexte.
  - Créer un gabarit de base et des gabarits enfants avec `extends`.
  - Découper l'interface en partials avec `include`.
  - Construire des URL avec la balise `% url %`.
  - Parcourir une liste avec `for` et afficher des conditions avec
    `if`.



## Pourquoi des gabarits ?

Dans le chapitre précédent, la vue renvoyait du HTML sous forme de chaîne Python.
Cette approche montre bien le mécanisme, mais elle ne tient pas longtemps :

  - le HTML se mélange au code Python ;
  - les guillemets et les accents deviennent difficiles à gérer ;
  - on ne peut pas réutiliser l'en-tête et le pied de page ;
  - un designer ne peut pas travailler sans toucher au Python.

Un gabarit est un fichier HTML contenant des balises Django. La vue
prépare les données, le gabarit les affiche. C'est le principe de séparation des
responsabilités : le « quoi » reste dans la vue, le « comment » va dans
le gabarit.


[A RETENIR]

Une vue calcule, un gabarit affiche. Si vous êtes tenté d'écrire des requêtes à la
base ou des règles métier dans un gabarit, arrêtez-vous : cette logique doit
remonter dans la vue ou dans le modèle.

[/A RETENIR]



## Configurer le moteur de gabarits

Django cherche les gabarits dans deux endroits :

  1. les dossiers listés dans `DIRS`, au niveau du projet ;
  2. les dossiers `templates/` des applications installées, si
    `APP_DIRS` vaut `True`.

Nous allons utiliser un dossier `templates/` à la racine du projet. Cela
facilite la vue d'ensemble et permet de partager `base.html` entre plusieurs
applications.


------------------------------------------------------------------------------
CODE : gesibiblio/settings.py, extrait
------------------------------------------------------------------------------
TEMPLATES = [
    {
        "BACKEND": "django.template.backends.django.DjangoTemplates",
        "DIRS": [BASE_DIR / "templates"],
        "APP_DIRS": True,
        "OPTIONS": {
            "context_processors": [
                "django.template.context_processors.debug",
                "django.template.context_processors.request",
                "django.contrib.auth.context_processors.auth",
                "django.contrib.messages.context_processors.messages",
            ],
        },
    },
]
------------------------------------------------------------------------------


  - `DIRS` : Liste des dossiers supplémentaires où chercher les gabarits.
  - `APP_DIRS` : Si `True`, Django cherche aussi dans
    `application/templates/`. C'est utile pour les applications réutilisables
    et pour l'administration.
  - `context_processors` : Fonctions qui ajoutent automatiquement des
    variables à tous les gabarits. `request` ajoute l'objet `request`,
    `auth` ajoute `user` et `perms`, `messages` ajoute les
    messages flash.

Créez le dossier `templates/` à la racine, puis les sous-dossiers :


------------------------------------------------------------------------------
CODE : Arborescence des gabarits
------------------------------------------------------------------------------
templates/
|-- base.html
|-- partials/
|   |-- navbar.html
|   `-- footer.html
`-- catalogue/
    |-- accueil.html
    `-- a_propos.html
------------------------------------------------------------------------------


[BONNE PRATIQUE]

Placez les gabarits d'une application dans un sous-dossier portant le nom de
l'application : `templates/catalogue/accueil.html`. Si deux applications
créent un fichier `accueil.html`, Django choisit le premier trouvé. Le
sous-dossier évite ces collisions et rend les chemins explicites.

[/BONNE PRATIQUE]



## Afficher un premier gabarit

Modifiez la vue d'accueil pour utiliser `render` :


------------------------------------------------------------------------------
CODE : catalogue/views.py
------------------------------------------------------------------------------
from django.shortcuts import render


def accueil(request):
    livres = [
        {"titre": "Le Petit Prince", "auteur": "Antoine de Saint-Exupéry"},
        {"titre": "Une si longue lettre", "auteur": "Mariama Bâ"},
        {"titre": "L'Étranger", "auteur": "Albert Camus"},
    ]
    return render(request, "catalogue/accueil.html", {"livres": livres})


def a_propos(request):
    return render(request, "catalogue/a_propos.html")
------------------------------------------------------------------------------


  - `render` : Raccourci qui charge un gabarit, le fusionne avec un
    contexte et renvoie une `HttpResponse`.
  - `"catalogue/accueil.html"` : Chemin du gabarit, relatif aux dossiers
    de gabarits.
  - `{"livres": livres}` : Contexte : un dictionnaire de variables
    accessibles dans le gabarit.

Créez `templates/catalogue/accueil.html` :


------------------------------------------------------------------------------
CODE : templates/catalogue/accueil.html
------------------------------------------------------------------------------
<h1>Bienvenue dans GesiBiblio</h1>
<p>La bibliothèque numérique de la formation.</p>

<h2>Quelques livres</h2>
<ul>
  {% for livre in livres %}
    <li>{{ livre.titre }} par {{ livre.auteur }}</li>
  {% empty %}
    <li>Aucun livre pour le moment.</li>
  {% endfor %}
</ul>
------------------------------------------------------------------------------

Rechargez la page. Les trois livres s'affichent. Le gabarit ne contient que du
HTML et des balises ; la liste vient de la vue.


[NOTE]

`{{ ... }}` affiche une valeur. `{% ... %}` exécute une balise
(boucle, condition, URL, etc.). Les espaces à l'intérieur des accolades sont
facultatifs mais recommandés pour la lisibilité.

[/NOTE]



## Le gabarit de base et l'héritage

Toutes les pages partagent le même en-tête, la même navigation et le même pied de
page. Recopier ce squelette dans chaque fichier serait une erreur. Django propose
l'héritage de gabarits.


[FIGURE] Le gabarit `base.html` définit des blocs. Les gabarits enfants remplissent ces blocs avec `extends`. Les partials sont inclus avec `include`.




### base.html


------------------------------------------------------------------------------
CODE : templates/base.html
------------------------------------------------------------------------------
{% load static %}
<!DOCTYPE html>
<html lang="fr">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>{% block titre %}GesiBiblio{% endblock %}</title>
  <link rel="stylesheet" href="{% static 'css/style.css' %}">
</head>
<body>
  {% include "partials/navbar.html" %}

  <main class="conteneur">
    {% block contenu %}{% endblock %}
  </main>

  {% include "partials/footer.html" %}
</body>
</html>
------------------------------------------------------------------------------


  - `{% load static %}` : Charge la bibliothèque de balises
    `static`, nécessaire pour les fichiers CSS, JavaScript et images.
  - `{% block titre %}` : Déclare une zone que les enfants peuvent
    remplacer. Le contenu entre `block` et `endblock` est la valeur par
    défaut.
  - `{% block contenu %}` : Zone principale de la page.
  - `{% include %}` : Insère un autre gabarit à cet endroit.



### Les gabarits enfants


------------------------------------------------------------------------------
CODE : templates/catalogue/accueil.html
------------------------------------------------------------------------------
{% extends "base.html" %}

{% block titre %}Accueil | GesiBiblio{% endblock %}

{% block contenu %}
  <h1>Bienvenue dans GesiBiblio</h1>
  <p>La bibliothèque numérique de la formation.</p>

  <h2>Quelques livres</h2>
  <ul>
    {% for livre in livres %}
      <li>{{ livre.titre }} par {{ livre.auteur }}</li>
    {% empty %}
      <li>Aucun livre pour le moment.</li>
    {% endfor %}
  </ul>
{% endblock %}
------------------------------------------------------------------------------


------------------------------------------------------------------------------
CODE : templates/catalogue/a_propos.html
------------------------------------------------------------------------------
{% extends "base.html" %}

{% block titre %}À propos | GesiBiblio{% endblock %}

{% block contenu %}
  <h1>À propos</h1>
  <p>GesiBiblio est un projet de formation réalisé avec Django.</p>
  <p>Il permet de gérer un catalogue, des membres et des emprunts.</p>
{% endblock %}
------------------------------------------------------------------------------


[ATTENTION]

`{% extends %}` doit être la première balise du gabarit, avant tout texte
ou espace significatif. Un fichier enfant ne peut étendre qu'un seul gabarit. Si
vous mettez du HTML avant `extends`, Django l'ignore ou provoque une erreur.

[/ATTENTION]



### Le mot-clé block.super

Si un enfant veut compléter le contenu du parent sans le remplacer, il utilise
`{{ block.super }}` :


------------------------------------------------------------------------------
CODE : Exemple de block.super
------------------------------------------------------------------------------
{% block titre %}{{ block.super }} | Catalogue{% endblock %}
------------------------------------------------------------------------------

Le titre devient « GesiBiblio | Catalogue ». C'est pratique pour ajouter un
suffixe commun à toutes les pages.



## Découper avec include

Les partials sont des morceaux de gabarit réutilisables : navigation, pied de page,
carte de livre, pagination.


------------------------------------------------------------------------------
CODE : templates/partials/navbar.html
------------------------------------------------------------------------------
<header class="entete">
  <nav class="conteneur barre">
    <a class="marque" href="{% url 'catalogue:accueil' %}">GesiBiblio</a>
    <ul class="menu">
      <li><a href="{% url 'catalogue:accueil' %}">Accueil</a></li>
      <li><a href="{% url 'catalogue:a_propos' %}">À propos</a></li>
    </ul>
  </nav>
</header>
------------------------------------------------------------------------------


------------------------------------------------------------------------------
CODE : templates/partials/footer.html
------------------------------------------------------------------------------
<footer class="pied">
  <div class="conteneur">
    <p>GesiBiblio, projet de formation Django.</p>
    <p>Formation propulsée par GESITECHNOLOGIES.</p>
  </div>
</footer>
------------------------------------------------------------------------------


[NOTE]

Un partial hérite du contexte de la page. Si `navbar.html` utilise
`user`, la variable est disponible parce que le processeur de contexte
`auth` l'ajoute à tous les gabarits. Pour passer une variable spécifique,
utilisez `{% include "partial.html" with livre=livre only %}`. Le
`only` isole le partial du reste du contexte, ce qui rend ses dépendances
explicites.

[/NOTE]



## Les URL dans les gabarits

La balise `url` construit une URL à partir du nom de la route :


------------------------------------------------------------------------------
CODE : Exemple
------------------------------------------------------------------------------
<a href="{% url 'catalogue:accueil' %}">Accueil</a>
<a href="{% url 'catalogue:livre_detail' livre.slug %}">Voir le livre</a>
------------------------------------------------------------------------------

Le premier argument est le nom complet, préfixé par `app_name`. Les arguments
suivants remplissent les paramètres de l'URL. Par exemple, si la route est
`path("livres/<slug:slug>/", ...)`, il faut passer le slug du livre.


[BONNE PRATIQUE]

N'écrivez jamais `href="/livres/le-petit-prince/"` en dur. Utilisez
`{% url %}`. Le jour où vous changez le préfixe `/livres/` en
`/catalogue/`, toutes les pages continuent de fonctionner.

[/BONNE PRATIQUE]



## Boucles et conditions

Le langage de gabarit propose les structures de base. Voici un aperçu, détaillé au
chapitre des balises et filtres.


------------------------------------------------------------------------------
CODE : templates/catalogue/accueil.html, extrait
------------------------------------------------------------------------------
{% if livres %}
  <ul>
    {% for livre in livres %}
      <li>
        {{ forloop.counter }}. {{ livre.titre }}
        {% if forloop.first %}(premier){% endif %}
      </li>
    {% endfor %}
  </ul>
{% else %}
  <p>Aucun livre disponible.</p>
{% endif %}
------------------------------------------------------------------------------


  - `forloop.counter` : Numéro de l'itération, à partir de 1.
  - `forloop.counter0` : Numéro de l'itération, à partir de 0.
  - `forloop.first` : Vrai pour le premier élément.
  - `forloop.last` : Vrai pour le dernier élément.
  - `{% empty %}` : Bloc exécuté si la liste est vide.



## Organiser ses gabarits

Il existe deux emplacements possibles :

  - `templates/` à la racine du projet, pour les gabarits partagés ;
  - `catalogue/templates/catalogue/` dans l'application, pour les
    gabarits propres au catalogue.

Pour ce module, nous utilisons le dossier racine `templates/`. C'est plus
simple à suivre pour un débutant et cela garde `base.html` visible. Dans un
projet réutilisable, l'emplacement dans l'application est préférable.


[ERREUR FREQUENTE]

Un fichier `base.html` placé directement dans `templates/` est trouvé par
toutes les applications. Si vous créez plus tard une application `blog` qui
possède aussi un `base.html`, vous aurez deux fichiers concurrents. Utilisez
des noms explicites, par exemple `base.html` pour le site et
`blog/base.html` pour l'application.

[/ERREUR FREQUENTE]

==============================================================================
CHAPITRE 5 : LES FICHIERS STATIQUES ET LE DESIGN
==============================================================================


Une page HTML brute est fonctionnelle, mais peu agréable. Dans ce chapitre, vous ajoutez une feuille de style complète, un logo, un favicon et un peu de JavaScript. Vous configurez aussi les fichiers média, c'est-à-dire les images envoyées par les utilisateurs, comme les couvertures de livres.


OBJECTIFS DU CHAPITRE


  - Distinguer fichiers statiques et fichiers média.
  - Configurer `STATIC_URL`, `STATICFILES_DIRS` et
    `STATIC_ROOT`.
  - Charger une feuille de style et des images avec `% static %`.
  - Écrire un CSS responsive pour le catalogue.
  - Ajouter un comportement JavaScript simple et accessible.
  - Configurer l'envoi et l'affichage des couvertures de livres.
  - Préparer les fichiers statiques pour la production avec
    `collectstatic`.



## Statique ou média ?


  - Fichiers statiques : Fichiers livrés avec le site et identiques pour tous
    les visiteurs : CSS, JavaScript, logo, favicon, icônes. Ils sont versionnés avec
    le code.
  - Fichiers média : Fichiers envoyés par les utilisateurs : couvertures de
    livres, photos de profil, pièces jointes. Ils changent pendant la vie du site et
    ne sont pas versionnés.


[A RETENIR]

Le CSS, le JavaScript et le logo sont des fichiers statiques. Une couverture de
livre téléversée par un bibliothécaire est un fichier média. Les deux utilisent des
URL, mais pas les mêmes réglages ni le même mode de service en production.

[/A RETENIR]



## Configurer les fichiers statiques

Ajoutez ces lignes dans `settings.py`, après `STATIC_URL` :


------------------------------------------------------------------------------
CODE : gesibiblio/settings.py, extrait
------------------------------------------------------------------------------
STATIC_URL = "static/"

# Dossiers où Django cherche les fichiers statiques en développement.
STATICFILES_DIRS = [
    BASE_DIR / "static",
]

# Dossier où collectstatic copie les fichiers pour la production.
STATIC_ROOT = BASE_DIR / "staticfiles"

# Fichiers envoyés par les utilisateurs.
MEDIA_URL = "media/"
MEDIA_ROOT = BASE_DIR / "media"
------------------------------------------------------------------------------


  - `STATIC_URL` : Préfixe des URL statiques. Avec `"static/"`,
    le fichier `static/css/style.css` est servi à l'adresse
    `/static/css/style.css`.
  - `STATICFILES_DIRS` : Dossiers supplémentaires scannés par Django.
    Ici, le dossier `static/` à la racine du projet.
  - `STATIC_ROOT` : Dossier de destination de `collectstatic`. Il ne
    faut pas le versionner.
  - `MEDIA_URL` : Préfixe des URL des fichiers envoyés.
  - `MEDIA_ROOT` : Dossier de stockage des fichiers envoyés.


[ATTENTION]

Ne confondez pas `STATICFILES_DIRS` et `STATIC_ROOT`.
`STATICFILES_DIRS` indique où vous écrivez vos fichiers.
`STATIC_ROOT` indique où `collectstatic` les rassemble pour la
production. Écrire directement dans `STATIC_ROOT` est une erreur.

[/ATTENTION]

Créez l'arborescence suivante :


------------------------------------------------------------------------------
CODE : Arborescence des fichiers statiques
------------------------------------------------------------------------------
static/
|-- css/
|   `-- style.css
|-- js/
|   `-- app.js
`-- img/
    |-- logo-gesibiblio.svg
    `-- favicon.svg

media/
`-- couvertures/

## Charger un fichier statique

Dans un gabarit, commencez par charger la bibliothèque `static`, puis utilisez
la balise `static` :


------------------------------------------------------------------------------
CODE : templates/base.html
------------------------------------------------------------------------------
{% load static %}
<!DOCTYPE html>
<html lang="fr">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>{% block titre %}GesiBiblio{% endblock %}</title>
  <link rel="stylesheet" href="{% static 'css/style.css' %}">
  <link rel="icon" href="{% static 'img/favicon.svg' %}" type="image/svg+xml">
</head>
<body>
  {% include "partials/navbar.html" %}
  {% include "partials/messages.html" %}

  <main class="conteneur">
    {% block contenu %}{% endblock %}
  </main>

  {% include "partials/footer.html" %}
  <script src="{% static 'js/app.js' %}" defer></script>
</body>
</html>
------------------------------------------------------------------------------


[ATTENTION]

`{% load static %}` doit apparaître dans chaque gabarit qui utilise
`{% static %}`. Le charger dans `base.html` ne le rend pas disponible
dans les gabarits enfants : chaque fichier a son propre contexte de bibliothèques.

[/ATTENTION]

## Le JavaScript

Le JavaScript reste minimal : ouvrir et fermer le menu sur mobile, et faire
disparaître les messages après quelques secondes.


------------------------------------------------------------------------------
CODE : static/js/app.js
------------------------------------------------------------------------------
const burger = document.querySelector(".burger");
const menu = document.querySelector("#menu-principal");

if (burger && menu) {
  burger.addEventListener("click", () => {
    const ouvert = menu.classList.toggle("ouvert");
    burger.setAttribute("aria-expanded", String(ouvert));
  });
}

document.querySelectorAll(".message").forEach((message) => {
  window.setTimeout(() => {
    message.classList.add("disparition");
  }, 5000);
});
------------------------------------------------------------------------------


[BONNE PRATIQUE]

Un site doit rester utilisable sans JavaScript. Ici, la navigation fonctionne même
si le script ne se charge pas : le menu est visible par défaut sur ordinateur et
les liens restent accessibles. Le JavaScript améliore l'expérience, il ne porte
pas toute la logique.

[/BONNE PRATIQUE]



## Les fichiers média

Les couvertures de livres sont envoyées par les utilisateurs. Elles ne sont pas
statiques : elles vivent dans `MEDIA_ROOT` et sont servies via
`MEDIA_URL`.



### Configuration


------------------------------------------------------------------------------
CODE : gesibiblio/settings.py, extrait
------------------------------------------------------------------------------
MEDIA_URL = "media/"
MEDIA_ROOT = BASE_DIR / "media"
------------------------------------------------------------------------------

En développement, Django doit servir ces fichiers. Ajoutez les lignes suivantes à
la fin du fichier `urls.py` du projet :


------------------------------------------------------------------------------
CODE : gesibiblio/urls.py
------------------------------------------------------------------------------
from django.conf import settings
from django.conf.urls.static import static
from django.contrib import admin
from django.urls import include, path

urlpatterns = [
    path("admin/", admin.site.urls),
    path("", include("catalogue.urls")),
]

if settings.DEBUG:
    urlpatterns += static(
        settings.MEDIA_URL,
        document_root=settings.MEDIA_ROOT,
    )
------------------------------------------------------------------------------


[ATTENTION]

`static()` ne fonctionne qu'en développement, lorsque `DEBUG` vaut
`True`. En production, Nginx ou un service de stockage doit servir les
fichiers média. Ne laissez jamais Django servir des fichiers envoyés par des
utilisateurs en production.

[/ATTENTION]



### Afficher une couverture

Dans un gabarit, testez d'abord la présence de l'image :


------------------------------------------------------------------------------
CODE : templates/catalogue/livres/carte.html
------------------------------------------------------------------------------
{% if livre.couverture %}
  <img src="{{ livre.couverture.url }}"
       alt="Couverture de {{ livre.titre }}">
{% else %}
  <div class="couverture-vide" aria-hidden="true">
    {{ livre.titre|first }}
  </div>
{% endif %}
------------------------------------------------------------------------------


[NOTE]

`livre.couverture` est un objet `ImageField`. `.url` renvoie
l'adresse publique du fichier, par exemple `/media/couvertures/le-petit-prince.jpg`.
L'image n'est accessible que si `MEDIA_URL` et `MEDIA_ROOT` sont
correctement configurés.

[/NOTE]



## Préparer la production

En développement, Django sert les fichiers statiques automatiquement. En
production, ce n'est pas le cas. La commande `collectstatic` rassemble tous
les fichiers dans `STATIC_ROOT` :


TERMINAL :
  $ python manage.py collectstatic

Le serveur web (Nginx, Apache) ou un service comme WhiteNoise sert ensuite ce
dossier. Une configuration typique avec WhiteNoise :


TERMINAL :
  $ python -m pip install whitenoise


------------------------------------------------------------------------------
CODE : gesibiblio/settings.py, extrait
------------------------------------------------------------------------------
MIDDLEWARE = [
    "django.middleware.security.SecurityMiddleware",
    "whitenoise.middleware.WhiteNoiseMiddleware",
    # ... autres middlewares
]

STORAGES = {
    "default": {
        "BACKEND": "django.core.files.storage.FileSystemStorage",
    },
    "staticfiles": {
        "BACKEND": "whitenoise.storage.CompressedManifestStaticFilesStorage",
    },
}
------------------------------------------------------------------------------


[BONNE PRATIQUE]

En production, utilisez un nom de fichier avec un hash, comme
`style.3f2a1c.css`, pour que les navigateurs mettent à jour le cache. Le
`CompressedManifestStaticFilesStorage` de WhiteNoise s'en charge. En
développement, gardez la configuration simple.

[/BONNE PRATIQUE]

==============================================================================
CHAPITRE 6 : LES BALISES ET LES FILTRES
==============================================================================


Le langage de gabarit de Django est volontairement limité. Il fournit des balises pour les boucles, les conditions et les URL, et des filtres pour transformer les valeurs à l'affichage. Dans ce chapitre, vous apprenez les balises et filtres essentiels, puis vous créez vos propres filtres et balises réutilisables.


OBJECTIFS DU CHAPITRE


  - Distinguer une variable, une balise et un filtre.
  - Utiliser les balises `if`, `for`, `with`, `url`,
    `include` et `csrf_token`.
  - Appliquer les filtres courants : `date`, `length`,
    `truncatewords`, `pluralize`, `yesno`.
  - Créer un filtre personnalisé et une balise simple.
  - Créer une balise d'inclusion pour réutiliser une carte de livre.
  - Comprendre l'échappement automatique et éviter les failles XSS.



## La syntaxe du langage de gabarit

Le langage de gabarit de Django utilise quatre formes :


------------------------------------------------------------------------------
CODE : Les quatre formes de base
------------------------------------------------------------------------------
{# Ceci est un commentaire court #}

{{ livre.titre }}

{{ livre.titre|upper }}

{{ livre.resume|truncatewords:20 }}

{% if livre.est_disponible %}
  <p>Disponible</p>
{% endif %}
------------------------------------------------------------------------------


  - `{{ ... }}` : Affiche une valeur. On parle de variable ou
    d'expression.
  - `{% ... %}` : Exécute une balise : boucle, condition, URL,
    inclusion, chargement de bibliothèque.
  - `{# ... #}` : Commentaire court, sur une seule ligne. Il n'est pas
    envoyé au navigateur.
  - `|filtre` : Transforme la valeur affichée. Les filtres se chaînent :
    `nom|lower|capfirst`.


[A RETENIR]

Le langage de gabarit n'est pas Python. Il ne permet pas d'appeler des fonctions
avec des arguments, d'importer des modules ou d'écrire des boucles complexes.
Cette limitation est volontaire : elle protège la séparation entre logique et
présentation.

[/A RETENIR]



## Les variables et la recherche par point

Dans `{{ livre.auteur.nom }}`, Django cherche dans cet ordre :

  1. la clé `"auteur"` dans un dictionnaire ;
  2. l'attribut `auteur` d'un objet ;
  3. la méthode `auteur()` sans argument ;
  4. l'index `auteur` d'une liste.

Puis il répète l'opération pour `.nom`. Cette recherche par point explique
pourquoi `{{ livre.titre }}` fonctionne aussi bien avec un dictionnaire
qu'avec un objet `Livre`.


------------------------------------------------------------------------------
CODE : Exemples de recherche
------------------------------------------------------------------------------
{{ livre.titre }}
{{ livre.auteur.nom }}
{{ livre.categories.all }}
{{ livres.0.titre }}
{{ user.get_full_name }}
------------------------------------------------------------------------------


[ATTENTION]

Si une variable n'existe pas, Django affiche une chaîne vide, sans erreur. C'est
pratique, mais cela peut masquer une faute de frappe. Si la page est vide à
l'endroit attendu, vérifiez le nom exact de la variable dans la vue.

[/ATTENTION]


[NOTE]

`{{ user.get_full_name }}` appelle la méthode `get_full_name()` sans
parenthèses. Le langage de gabarit ajoute automatiquement les parenthèses pour les
méthodes qui n'attendent aucun argument. Une méthode qui exige un argument ne peut
pas être appelée directement.

[/NOTE]



## Les balises essentielles



### if, elif, else


------------------------------------------------------------------------------
CODE : Conditions
------------------------------------------------------------------------------
{% if livre.est_disponible %}
  <span class="badge badge-disponible">Disponible</span>
{% elif livre.statut == "reserve" %}
  <span class="badge badge-indisponible">Réservé</span>
{% else %}
  <span class="badge badge-indisponible">Indisponible</span>
{% endif %}
------------------------------------------------------------------------------

Les opérateurs disponibles sont `==`, `!=`, `<`, `>`,
`<=`, `>=`, `in`, `not in`, `is`, `is not`,
`and`, `or` et `not`. Les parenthèses ne sont pas autorisées : on
combine avec `and` et `or`, en gardant des conditions simples.


[ATTENTION]

`{% if livre }}` teste la vérité de l'objet. Un objet Django est
généralement vrai, même s'il n'a pas de titre. Pour tester une chaîne vide,
utilisez `{% if livre.titre }}`. Pour tester une liste vide, utilisez
`{% if livres }}`.

[/ATTENTION]



### for et empty


------------------------------------------------------------------------------
CODE : Boucle avec forloop
------------------------------------------------------------------------------
<ul>
  {% for livre in livres %}
    <li>
      {{ forloop.counter }}. {{ livre.titre }}
      {% if forloop.first %}(nouveauté){% endif %}
      {% if forloop.last %}(dernier de la liste){% endif %}
    </li>
  {% empty %}
    <li>Aucun livre pour le moment.</li>
  {% endfor %}
</ul>
------------------------------------------------------------------------------


  - `forloop.counter` : Compteur à partir de 1.
  - `forloop.counter0` : Compteur à partir de 0.
  - `forloop.revcounter` : Compteur à rebours, fin à 1.
  - `forloop.first` : Vrai au premier tour.
  - `forloop.last` : Vrai au dernier tour.
  - `forloop.parentloop` : Boucle parente, dans une boucle imbriquée.

On peut parcourir un dictionnaire :


------------------------------------------------------------------------------
CODE : Boucle sur un dictionnaire
------------------------------------------------------------------------------
{% for cle, valeur in statistiques.items %}
  <p>{{ cle }} : {{ valeur }}</p>
{% endfor %}
------------------------------------------------------------------------------

Et inverser une liste avec le filtre `reversed` :


------------------------------------------------------------------------------
CODE : Boucle inversée
------------------------------------------------------------------------------
{% for livre in livres reversed %}
  <p>{{ livre.titre }}</p>
{% endfor %}
------------------------------------------------------------------------------

CODE : Alias avec with

{% with auteur=livre.auteur.nom_complet %}

  <p>Initiales : {{ auteur|initiales }}.</p>
{% endwith %}

### csrf_token

Tout formulaire `POST` doit contenir |{
jeton, Django refuse la requête avec une erreur `403 Forbidden`.


------------------------------------------------------------------------------
CODE : Jeton CSRF
------------------------------------------------------------------------------
<form method="post">
  {% csrf_token %}
  <input type="text" name="titre">
  <button type="submit">Enregistrer</button>
</form>
------------------------------------------------------------------------------


[ATTENTION]

`csrf_token` protège contre les attaques CSRF, qui consistent à faire
envoyer un formulaire à un utilisateur connecté depuis un autre site. Ne
désactivez jamais cette protection sans raison très précise.

[/ATTENTION]



### include, extends et block


------------------------------------------------------------------------------
CODE : Inclusion et héritage
------------------------------------------------------------------------------
{% extends "base.html" %}

{% block contenu %}
  {% include "partials/entete.html" %}
  <p>Contenu de la page.</p>
{% endblock %}
------------------------------------------------------------------------------

`include` insère un gabarit complet. `extends` établit une relation
d'héritage. Un gabarit enfant ne peut pas utiliser `extends` et être inclus
en même temps : choisissez l'un ou l'autre.



### comment, autoescape, now, firstof, cycle


------------------------------------------------------------------------------
CODE : Balises utilitaires
------------------------------------------------------------------------------
{% comment %}
  Ce bloc est ignoré par Django.
  Utile pour désactiver temporairement du code.
{% endcomment %}

{% autoescape off %}
  {{ contenu_html }}
{% endautoescape %}

<p>Nous sommes le {% now "d/m/Y" %}.</p>

<p>{{ livre.sous_titre|default:livre.titre }}</p>

{% firstof livre.sous_titre livre.titre "Sans titre" %}

{% for i in "123" %}
  <span class="{% cycle 'pair' 'impair' %}">{{ i }}</span>
{% endfor %}
------------------------------------------------------------------------------


[ATTENTION]

`autoescape off` désactive l'échappement HTML pour toute la zone. Ne
l'utilisez jamais avec du contenu fourni par un utilisateur. Nous y revenons à la
fin du chapitre.

[/ATTENTION]

{% endverbatim %}

## Les filtres essentiels

Un filtre se place après une valeur, séparé par une barre verticale. Certains
acceptent un argument après deux-points.

Expression & Résultat

`{{ livre.titre|upper }}` & Le titre en majuscules.
`{{ livre.titre|lower }}` & Le titre en minuscules.
`{{ livre.titre|title }}` & Chaque mot commence par une majuscule.
`{{ livre.titre|capfirst }}` & Seule la première lettre est en majuscule.
`{{ livre.titre|length }}` & Le nombre de caractères.
`{{ livres|length }}` & Le nombre d'éléments de la liste.
`{{ livre.resume|truncatechars:80 }}` & Coupe à 80 caractères.
`{{ livre.resume|truncatewords:15 }}` & Coupe à 15 mots.
`{{ livre.date_publication|date:"d/m/Y" }}` & Une date au format français.
`{{ livre.prix|floatformat:2 }}` & Deux chiffres après la virgule.
`{{ livre.categories.all|join:", " }}` & Joint les catégories par une virgule.
`{{ livre.nombre_exemplaires|pluralize }}` & Ajoute « s » si le nombre est différent de 1.
`{{ livre.est_disponible|yesno:"Oui,Non" }}` & Affiche Oui ou Non.
`{{ livre.titre|slugify }}` & Transforme le titre en slug.
`{{ livre.resume|linebreaks }}` & Transforme les sauts de ligne en paragraphes.
`{{ livre.resume|striptags }}` & Supprime les balises HTML.



### default et default_if_none


------------------------------------------------------------------------------
CODE : Valeurs par défaut
------------------------------------------------------------------------------
{{ livre.sous_titre|default:"Sans sous-titre" }}
{{ livre.editeur|default_if_none:"Éditeur inconnu" }}
{{ livre.annee|default:"Année inconnue" }}
------------------------------------------------------------------------------

`default` remplace les valeurs fausses : chaîne vide, zéro, liste vide,
`None`. `default_if_none` ne remplace que `None`. La différence
compte pour un nombre : `0|default:"Non renseigné"` affiche
« Non renseigné », alors que `0|default_if_none:"Non renseigné"`
affiche `0`.



### date et time


------------------------------------------------------------------------------
CODE : Formats de date
------------------------------------------------------------------------------
{{ livre.date_publication|date:"d/m/Y" }}
{{ livre.date_publication|date:"l j F Y" }}
{{ emprunt.date_emprunt|date:"D d M Y" }}
{{ maintenant|time:"H:i" }}
------------------------------------------------------------------------------

Les formats les plus utilisés : `d` (jour sur deux chiffres), `j`
(jour sans zéro), `m` (mois sur deux chiffres), `F` (mois en toutes
lettres), `Y` (année sur quatre chiffres), `H` (heure sur 24 heures),
`i` (minutes), `s` (secondes).



### pluralize et yesno


------------------------------------------------------------------------------
CODE : Accords et booléens
------------------------------------------------------------------------------
<p>
  {{ page_obj.paginator.count }} livre{{ page_obj.paginator.count|pluralize }}
</p>
<p>{{ livre.est_disponible|yesno:"Disponible,Indisponible" }}</p>
------------------------------------------------------------------------------

`pluralize` ajoute un « s » par défaut. On peut préciser deux formes :
`pluralize:"y,ies"` pour « copy » et « copies ».



### linebreaks, escape et safe


------------------------------------------------------------------------------
CODE : Texte et HTML
------------------------------------------------------------------------------
{{ livre.resume|linebreaks }}
{{ livre.resume|linebreaksbr }}
{{ commentaire|escape }}
{{ contenu|safe }}
------------------------------------------------------------------------------


[ATTENTION]

`linebreaks` échappe le contenu, puis ajoute des balises `<p>` et
`<br>`. `safe` ne fait aucun échappement : il déclare que la chaîne est
déjà du HTML sûr. Utilisez `safe` uniquement sur du contenu que vous
contrôlez entièrement.

[/ATTENTION]



## Créer ses propres filtres et balises

Les filtres intégrés couvrent la majorité des besoins. Pour les cas spécifiques,
Django permet d'écrire ses propres bibliothèques de balises.



### L'arborescence

Créez un dossier `templatetags/` dans l'application, avec un fichier
`__init__.py` vide :


------------------------------------------------------------------------------
CODE : Arborescence des balises personnalisées
------------------------------------------------------------------------------
catalogue/
|-- templatetags/
|   |-- __init__.py
|   `-- biblio.py
|-- models.py
`-- views.py
------------------------------------------------------------------------------


[ATTENTION]

Le dossier doit s'appeler exactement `templatetags`, au pluriel, et se trouver
dans l'application. Le fichier `__init__.py` est obligatoire : sans lui,
Django ne voit pas le paquet. Redémarrez le serveur après la création.

[/ATTENTION]



### Un filtre personnalisé


------------------------------------------------------------------------------
CODE : catalogue/templatetags/biblio.py
------------------------------------------------------------------------------
from django import template

register = template.Library()


@register.filter
def initiales(nom_complet):
    """Retourne les initiales d'un nom, par exemple AS."""
    morceaux = nom_complet.split()
    return "".join(morceau[0] for morceau in morceaux[:2]).upper()
------------------------------------------------------------------------------

Utilisation dans un gabarit :


------------------------------------------------------------------------------
CODE : Utilisation du filtre
------------------------------------------------------------------------------
{% load biblio %}
<p>{{ livre.auteur }} ({{ livre.auteur|initiales }})</p>
------------------------------------------------------------------------------


[NOTE]

Le nom du filtre est le nom de la fonction. On peut le changer avec
`@register.filter(name="sigle")`. Le nom doit être un identifiant valide et
ne pas contenir d'espace.

[/NOTE]



### Une balise simple

Une balise simple renvoie une valeur. Elle peut recevoir des arguments.


------------------------------------------------------------------------------
CODE : catalogue/templatetags/biblio.py, extrait
------------------------------------------------------------------------------
@register.simple_tag
def cote(auteur, annee):
    """Construit une cote simple, par exemple S1943."""
    return f"{auteur[0].upper()}{annee}"
------------------------------------------------------------------------------


------------------------------------------------------------------------------
CODE : Utilisation de la balise
------------------------------------------------------------------------------
{% load biblio %}
<p>Cote : {% cote livre.auteur.nom livre.annee %}</p>
------------------------------------------------------------------------------



### Une balise d'inclusion

Une balise d'inclusion rend un gabarit avec un contexte. C'est la manière propre
de réutiliser un composant, comme une carte de livre.


------------------------------------------------------------------------------
CODE : catalogue/templatetags/biblio.py, extrait
------------------------------------------------------------------------------
@register.inclusion_tag("catalogue/livres/carte.html")
def carte_livre(livre):
    return {"livre": livre}
------------------------------------------------------------------------------


------------------------------------------------------------------------------
CODE : templates/catalogue/livres/carte.html
------------------------------------------------------------------------------
{% load biblio %}
<article class="carte-livre">
  <div class="couverture-vide" aria-hidden="true">
    {{ livre.titre|first }}
  </div>
  <h3>{{ livre.titre|truncatechars:38 }}</h3>
  <p class="auteur">{{ livre.auteur }}</p>
  <span class="badge badge-disponible">
    {{ livre.annee|default:"Année inconnue" }}
  </span>
</article>
------------------------------------------------------------------------------


------------------------------------------------------------------------------
CODE : Utilisation dans la page d'accueil
------------------------------------------------------------------------------
{% load biblio %}

<div class="grille-livres">
  {% for livre in livres %}
    {% carte_livre livre %}
  {% endfor %}
</div>
------------------------------------------------------------------------------


  - `inclusion_tag` : Déclare une balise qui rend un gabarit. Le
    dictionnaire renvoyé devient le contexte du gabarit.
  - `takes_context=True` : Permet à la balise de recevoir le contexte
    complet, par exemple pour lire `request.GET`.



### Une balise avec contexte

Pour construire un lien de pagination qui conserve les filtres de recherche, la
balise a besoin de la requête :


------------------------------------------------------------------------------
CODE : catalogue/templatetags/biblio.py, extrait
------------------------------------------------------------------------------
@register.simple_tag(takes_context=True)
def url_page(context, numero):
    """Construit un lien ?page=N en conservant les autres paramètres."""
    params = context["request"].GET.copy()
    params["page"] = numero
    return f"?{params.urlencode()}"
------------------------------------------------------------------------------


------------------------------------------------------------------------------
CODE : Utilisation
------------------------------------------------------------------------------
<a href="{% url_page page_obj.previous_page_number %}">Précédent</a>
<a href="{% url_page page_obj.next_page_number %}">Suivant</a>
------------------------------------------------------------------------------


[NOTE]

`context["request"]` est disponible grâce au processeur de contexte
`django.template.context_processors.request`, présent dans
`settings.py`. Sans lui, la balise lèverait une erreur
`KeyError: 'request'`.

[/NOTE]

## Sécurité : échappement et XSS

Django échappe automatiquement les variables. Si un utilisateur enregistre une
balise `<script>` contenant du code JavaScript dans le résumé d'un livre, le
gabarit affiche le texte au lieu de l'exécuter.


------------------------------------------------------------------------------
CODE : Échappement automatique
------------------------------------------------------------------------------
{{ livre.resume }}
------------------------------------------------------------------------------

Le navigateur reçoit :


------------------------------------------------------------------------------
CODE : HTML produit
------------------------------------------------------------------------------
&lt;script&gt;alert("xss")&lt;/script&gt;
------------------------------------------------------------------------------

Avec `|safe`, le script serait exécuté. C'est une faille XSS.


------------------------------------------------------------------------------
CODE : À ne jamais faire avec une donnée utilisateur
------------------------------------------------------------------------------
{{ livre.resume|safe }}
------------------------------------------------------------------------------


[ATTENTION]

Les filtres `escape` et l'échappement automatique sont vos amis. Si vous
avez besoin d'afficher du HTML riche, utilisez une bibliothèque de nettoyage comme
`bleach` ou `nh3`, puis marquez le résultat comme sûr uniquement après
nettoyage. Ne faites jamais confiance à une chaîne envoyée par un utilisateur.

[/ATTENTION]


[BONNE PRATIQUE]

Règle simple : pas de `safe` sur les champs remplis par les utilisateurs. Pour
les sauts de ligne, utilisez `linebreaks` ou `linebreaksbr`, qui
échappent le contenu avant d'ajouter les balises.

[/BONNE PRATIQUE]

## Le modèle et l'ORM

Un modèle Django est une classe Python qui décrit une table de la base de
données. Chaque attribut de classe devient une colonne. Chaque instance devient une
ligne. Django traduit automatiquement les opérations Python en SQL : c'est
l'ORM, pour Object Relational Mapper.


------------------------------------------------------------------------------
CODE : Principe de l'ORM
------------------------------------------------------------------------------
# Python
livre = Livre.objects.get(slug="le-petit-prince")
print(livre.titre)

# SQL équivalent, exécuté par Django
# SELECT * FROM catalogue_livre WHERE slug = 'le-petit-prince' LIMIT 1;
------------------------------------------------------------------------------

L'ORM apporte trois avantages :

  - on écrit du Python, pas du SQL spécifique à une base ;
  - les requêtes sont paramétrées, ce qui protège des injections SQL ;
  - les relations sont manipulées comme des objets, avec
    `livre.auteur` ou `auteur.livres.all()`.


[A RETENIR]

Un modèle décrit les données et les règles qui les concernent. La vue ne doit pas
connaître le SQL. Elle interroge les modèles, qui centralisent la logique d'accès
aux données.

[/A RETENIR]



## Concevoir la base de données

Avant d'écrire du code, prenons le temps de dessiner les données.


[FIGURE] Modèle de données de GesiBiblio. Les clés étrangères matérialisent les relations entre les entités.



  - Auteur : Un auteur peut écrire plusieurs livres. Un livre a un seul auteur.
    C'est une relation « un à plusieurs ».
  - Catégorie : Un livre peut appartenir à plusieurs catégories, et une
    catégorie contient plusieurs livres. C'est une relation « plusieurs à
    plusieurs ».
  - Membre : Un membre est lié à un utilisateur Django par une relation
    « un à un ». Un utilisateur possède au plus un profil de membre.
  - Emprunt : Un emprunt relie un livre et un membre. Un livre peut avoir
    plusieurs emprunts dans le temps, un membre aussi.


[NOTE]

Un livre possède un nombre d'exemplaires. Le nombre d'exemplaires disponibles
n'est pas stocké : il se calcule en soustrayant les emprunts en cours. Stocker une
valeur calculable est une source d'incohérence. Nous utiliserons une propriété
Python.

[/NOTE]



## Écrire les modèles

Ouvrez `catalogue/models.py` et remplacez son contenu par le code suivant.
Les commentaires expliquent les choix importants.


------------------------------------------------------------------------------
CODE : catalogue/models.py
------------------------------------------------------------------------------
from django.conf import settings
from django.core.validators import (
    MaxValueValidator,
    MinValueValidator,
    RegexValidator,
)
from django.db import models
from django.urls import reverse
from django.utils import timezone


class Categorie(models.Model):
    nom = models.CharField(max_length=80, unique=True)
    slug = models.SlugField(max_length=90, unique=True)
    description = models.TextField(blank=True)

    class Meta:
        ordering = ["nom"]
        verbose_name = "catégorie"
        verbose_name_plural = "catégories"

    def __str__(self):
        return self.nom

    def get_absolute_url(self):
        return reverse(
            "catalogue:categorie_detail",
            kwargs={"slug": self.slug},
        )


class Auteur(models.Model):
    prenom = models.CharField(max_length=80)
    nom = models.CharField(max_length=80)
    biographie = models.TextField(blank=True)
    date_naissance = models.DateField(null=True, blank=True)

    class Meta:
        ordering = ["nom", "prenom"]
        verbose_name = "auteur"
        verbose_name_plural = "auteurs"
        constraints = [
            models.UniqueConstraint(
                fields=["nom", "prenom"],
                name="auteur_unique_nom_prenom",
            ),
        ]

    def __str__(self):
        return f"{self.prenom} {self.nom}"

    @property
    def nom_complet(self):
        return f"{self.prenom} {self.nom}"


class Livre(models.Model):
    class Statut(models.TextChoices):
        DISPONIBLE = "disponible", "Disponible"
        EMPRUNTE = "emprunte", "Emprunté"
        RESERVE = "reserve", "Réservé"
        PERDU = "perdu", "Perdu"

    titre = models.CharField(max_length=200)
    sous_titre = models.CharField(max_length=200, blank=True)
    slug = models.SlugField(max_length=220, unique=True)
    isbn = models.CharField(
        max_length=13,
        unique=True,
        validators=[
            RegexValidator(
                r"^\d{13}$",
                "L'ISBN doit contenir exactement 13 chiffres.",
            ),
        ],
    )
    auteur = models.ForeignKey(
        Auteur,
        on_delete=models.PROTECT,
        related_name="livres",
    )
    categories = models.ManyToManyField(
        Categorie,
        related_name="livres",
        blank=True,
    )
    editeur = models.CharField(max_length=120, blank=True)
    annee_publication = models.PositiveIntegerField(
        validators=[
            MinValueValidator(1450),
            MaxValueValidator(2100),
        ],
    )
    nombre_exemplaires = models.PositiveIntegerField(default=1)
    couverture = models.ImageField(
        upload_to="couvertures/",
        blank=True,
        null=True,
    )
    resume = models.TextField(blank=True)
    statut = models.CharField(
        max_length=20,
        choices=Statut.choices,
        default=Statut.DISPONIBLE,
    )
    cree_le = models.DateTimeField(auto_now_add=True)
    modifie_le = models.DateTimeField(auto_now=True)

    class Meta:
        ordering = ["titre"]
        verbose_name = "livre"
        verbose_name_plural = "livres"
        indexes = [
            models.Index(fields=["titre"]),
        ]

    def __str__(self):
        return self.titre

    def get_absolute_url(self):
        return reverse(
            "catalogue:livre_detail",
            kwargs={"slug": self.slug},
        )

    @property
    def exemplaires_disponibles(self):
        emprunts_en_cours = self.emprunts.filter(
            date_retour__isnull=True
        ).count()
        return max(self.nombre_exemplaires - emprunts_en_cours, 0)

    @property
    def est_disponible(self):
        return (
            self.statut == self.Statut.DISPONIBLE
            and self.exemplaires_disponibles > 0
        )


class Membre(models.Model):
    user = models.OneToOneField(
        settings.AUTH_USER_MODEL,
        on_delete=models.CASCADE,
        related_name="membre",
    )
    numero = models.CharField(max_length=12, unique=True)
    telephone = models.CharField(max_length=20, blank=True)
    adresse = models.CharField(max_length=255, blank=True)
    date_inscription = models.DateField(auto_now_add=True)
    actif = models.BooleanField(default=True)

    class Meta:
        ordering = ["numero"]
        verbose_name = "membre"
        verbose_name_plural = "membres"

    def __str__(self):
        nom = self.user.get_full_name() or self.user.username
        return f"{nom} ({self.numero})"


class Emprunt(models.Model):
    livre = models.ForeignKey(
        Livre,
        on_delete=models.PROTECT,
        related_name="emprunts",
    )
    membre = models.ForeignKey(
        Membre,
        on_delete=models.PROTECT,
        related_name="emprunts",
    )
    date_emprunt = models.DateField(default=timezone.localdate)
    date_retour_prevue = models.DateField()
    date_retour = models.DateField(null=True, blank=True)
    remarque = models.TextField(blank=True)

    class Meta:
        ordering = ["-date_emprunt"]
        verbose_name = "emprunt"
        verbose_name_plural = "emprunts"
        constraints = [
            models.CheckConstraint(
                condition=models.Q(
                    date_retour_prevue__gte=models.F("date_emprunt")
                ),
                name="emprunt_retour_apres_emprunt",
            ),
        ]

    def __str__(self):
        return f"{self.livre} -> {self.membre}"

    @property
    def est_en_retard(self):
        if self.date_retour:
            return False
        return self.date_retour_prevue < timezone.localdate()

    @property
    def duree_retard(self):
        if not self.est_en_retard:
            return 0
        return (timezone.localdate() - self.date_retour_prevue).days
------------------------------------------------------------------------------


[ATTENTION]

La contrainte `CheckConstraint` utilise l'argument `condition` à partir
de Django 5.1. Avec Django 5.0 et les versions précédentes, l'argument s'appelle
`check`. Si vous utilisez une version plus ancienne, adaptez cette ligne.

[/ATTENTION]

`DateTimeField` | Date et heure.
`ImageField` | Image. Nécessite Pillow.
`FileField` | Fichier quelconque.

Tableau : Les types de champs les plus utilisés.



### null ou blank ?


  - `null=True` : Autorise la valeur `NULL` dans la base. À réserver
    aux champs non textuels : dates, nombres, relations.
  - `blank=True` : Autorise une valeur vide dans les formulaires. Pour un
    `CharField`, la valeur enregistrée est une chaîne vide, pas `NULL`.


[BONNE PRATIQUE]

Pour un `CharField` ou un `TextField`, utilisez `blank=True` sans
`null=True`. Sinon, vous aurez deux représentations du vide : `NULL` et
`""`. Pour un `DateField` ou une `ForeignKey` optionnelle, utilisez
les deux.

[/BONNE PRATIQUE]



### Les choix avec TextChoices

`Livre.Statut` est une classe imbriquée qui hérite de `models.TextChoices`.
Elle associe une valeur stockée en base à un libellé affiché :


------------------------------------------------------------------------------
CODE : Utilisation des choix
------------------------------------------------------------------------------
livre.statut = Livre.Statut.EMPRUNTE
livre.get_statut_display()   # "Emprunté"
------------------------------------------------------------------------------


[BONNE PRATIQUE]

Utilisez `TextChoices` plutôt qu'une liste de tuples. Le code devient plus
lisible, les valeurs sont centralisées et les libellés sont traduisibles.

[/BONNE PRATIQUE]



## Les relations et on_delete



### ForeignKey


------------------------------------------------------------------------------
CODE : Relation un à plusieurs
------------------------------------------------------------------------------
auteur = models.ForeignKey(
    Auteur,
    on_delete=models.PROTECT,
    related_name="livres",
)
------------------------------------------------------------------------------


  - `livre.auteur` renvoie l'objet `Auteur`.
  - `auteur.livres.all()` renvoie les livres de cet auteur.
  - `related_name` remplace le nom par défaut `livre_set`. Il rend
    le code plus lisible.



### ManyToManyField


------------------------------------------------------------------------------
CODE : Relation plusieurs à plusieurs
------------------------------------------------------------------------------
categories = models.ManyToManyField(
    Categorie,
    related_name="livres",
    blank=True,
)
------------------------------------------------------------------------------

Django crée une table intermédiaire. La méthode `add` associe une catégorie
à un livre, et `livre.categories.all()` renvoie ses catégories.



### OneToOneField


------------------------------------------------------------------------------
CODE : Relation un à un
------------------------------------------------------------------------------
user = models.OneToOneField(
    settings.AUTH_USER_MODEL,
    on_delete=models.CASCADE,
    related_name="membre",
)
------------------------------------------------------------------------------

Chaque utilisateur possède au plus un profil `Membre`. On accède au profil
avec `request.user.membre`. Attention : si le profil n'existe pas, l'accès
lève une exception `RelatedObjectDoesNotExist`. Nous le créerons
automatiquement à l'inscription.



### Les comportements on_delete


Valeur | Comportement
`CASCADE` | Supprime aussi les objets liés.
`PROTECT` | Empêche la suppression tant qu'un objet lié existe.
`RESTRICT` | Empêche la suppression, avec une erreur plus récente que
`PROTECT`.
`SET_NULL` | Met la clé étrangère à `NULL`. Nécessite
`null=True`.
`SET_DEFAULT` | Met la valeur par défaut.
`DO_NOTHING` | Ne fait rien. Risque d'incohérence, à éviter.

Tableau : Comportements possibles lors de la suppression d'un objet lié.


[BONNE PRATIQUE]

Pour un catalogue, `PROTECT` est souvent le bon choix : on ne supprime pas un
auteur qui a encore des livres, ni un livre qui a des emprunts. Pour un profil
utilisateur, `CASCADE` est logique : supprimer le compte supprime le profil.

[/BONNE PRATIQUE]



## Les options Meta et les contraintes

La classe `Meta` configure le modèle :

  - `ordering` : ordre par défaut des requêtes ;
  - `verbose_name` et `verbose_name_plural` : libellés dans
    l'administration ;
  - `indexes` : index de base de données ;
  - `constraints` : contraintes d'unicité ou de validation.


------------------------------------------------------------------------------
CODE : Meta du modèle Livre
------------------------------------------------------------------------------
class Meta:
    ordering = ["titre"]
    indexes = [
        models.Index(fields=["titre"]),
    ]
------------------------------------------------------------------------------


[NOTE]

Un index accélère certaines lectures mais ralentit les écritures et occupe de
l'espace. `unique=True` crée déjà un index : inutile d'ajouter
`db_index=True` sur un champ unique. Les recherches `icontains` avec
un joker en tête ne profitent pas toujours d'un index classique.

[/NOTE]

def exemplaires_disponibles(self):

## Les migrations

Une migration est un fichier Python qui décrit une modification du schéma. Django
la génère à partir de vos modèles.



### Créer la migration


TERMINAL :
  $ python manage.py makemigrations catalogue

Sortie attendue :


TERMINAL :
  $ Migrations for 'catalogue':
  $   catalogue/migrations/0001_initial.py
  $     + Create model Categorie
  $     + Create model Auteur
  $     + Create model Livre
  $     + Create model Membre
  $     + Create model Emprunt

Le fichier `0001_initial.py` contient les opérations. On peut le lire, mais
on ne le modifie pas à la main après l'avoir appliqué.



### Inspecter le SQL


TERMINAL :
  $ python manage.py sqlmigrate catalogue 0001

Vous voyez les ordres `CREATE TABLE`, les clés étrangères et les index. C'est
utile pour comprendre ce que Django fait réellement.



### Appliquer la migration


TERMINAL :
  $ python manage.py migrate

Sortie :


TERMINAL :
  $ Operations to perform:
  $   Apply all migrations: admin, auth, catalogue, contenttypes, sessions
  $ Running migrations:
  $   Applying catalogue.0001_initial... OK



### Vérifier l'état


TERMINAL :
  $ python manage.py showmigrations catalogue


TERMINAL :
  $ catalogue
  $  [X] 0001_initial

La croix indique que la migration est appliquée.


[BONNE PRATIQUE]

Versionnez toujours le dossier `migrations/`. Ne supprimez pas les fichiers
après les avoir appliqués. Pour renommer une migration, utilisez
`makemigrations --name` avant de l'appliquer. En production, sauvegardez la
base avant toute migration.

[/BONNE PRATIQUE]


[ERREUR FREQUENTE]

Si vous modifiez un modèle et que `migrate` ne fait rien, c'est que vous avez
oublié `makemigrations`. Si `makemigrations` ne détecte aucun changement
alors que vous avez modifié le fichier, vérifiez que l'application est bien dans
`INSTALLED_APPS` et que le serveur n'utilise pas un autre fichier.

[/ERREUR FREQUENTE]

### Créer des données


------------------------------------------------------------------------------
CODE : Shell Django
------------------------------------------------------------------------------
from catalogue.models import Auteur, Categorie, Livre

auteur = Auteur.objects.create(
    prenom="Antoine",
    nom="Saint-Exupéry",
    biographie="Aviateur et écrivain français.",

roman = Categorie.objects.create(nom="Roman", slug="roman")
livre = Livre.objects.create(
    titre="Le Petit Prince",
    slug="le-petit-prince",
    isbn="9782070612758",
    auteur=auteur,
    annee_publication=1943,
    nombre_exemplaires=3,
    resume="Un aviateur rencontre un petit prince.",
)
livre.categories.add(roman)
livre
------------------------------------------------------------------------------

L'affichage de `livre` utilise `__str__` et renvoie
`<Livre: Le Petit Prince>`.



### Lire des données


------------------------------------------------------------------------------
CODE : Requêtes de base
------------------------------------------------------------------------------
Livre.objects.count()
Livre.objects.all()
Livre.objects.get(slug="le-petit-prince")
Livre.objects.filter(titre__icontains="prince")
Livre.objects.exclude(statut="perdu")
Livre.objects.filter(annee_publication__gte=1900)
Livre.objects.filter(auteur__nom="Camus")
Livre.objects.order_by("titre")
Livre.objects.values_list("titre", flat=True)
Livre.objects.exists()
------------------------------------------------------------------------------


  - `get()` : Renvoie un objet et un seul. Lève `DoesNotExist` si
    aucun objet ne correspond, `MultipleObjectsReturned` si plusieurs.
  - `filter()` : Renvoie un `QuerySet`, même vide.
  - `icontains` : Recherche insensible à la casse.
  - `gte` : Supérieur ou égal. Autres suffixes : `gt`, `lt`,
    `lte`, `startswith`, `endswith`, `in`.



### Les objets Q et F

`Q` combine des conditions avec `|` (ou) et `&` (et) :


------------------------------------------------------------------------------
CODE : Conditions complexes
------------------------------------------------------------------------------
from django.db.models import Q

Livre.objects.filter(
    Q(titre__icontains="prince") | Q(isbn__icontains="978")
)
------------------------------------------------------------------------------

`F` référence un champ dans la requête, sans le charger en Python :


------------------------------------------------------------------------------
CODE : Expression F
------------------------------------------------------------------------------
from django.db.models import F

Livre.objects.filter(
    nombre_exemplaires__gt=1
).update(nombre_exemplaires=F("nombre_exemplaires") + 1)
------------------------------------------------------------------------------


[ATTENTION]

`update()` modifie directement en base et ne déclenche pas les méthodes
`save()` des modèles. Les signaux `pre_save` et `post_save` ne
sont pas exécutés. Utilisez-le pour des mises à jour de masse, pas pour une
logique métier complexe.

[/ATTENTION]



### select_related et prefetch_related

Le problème N+1 se produit lorsqu'une boucle déclenche une requête par élément :


------------------------------------------------------------------------------
CODE : Problème N+1
------------------------------------------------------------------------------
for livre in Livre.objects.all():
    print(livre.auteur.nom)   # une requête par livre
------------------------------------------------------------------------------

Pour une clé étrangère, utilisez `select_related` :


------------------------------------------------------------------------------
CODE : Requête optimisée
------------------------------------------------------------------------------
for livre in Livre.objects.select_related("auteur"):
    print(livre.auteur.nom)   # une seule requête
------------------------------------------------------------------------------

Pour une relation plusieurs à plusieurs ou une relation inverse, utilisez
`prefetch_related` :


------------------------------------------------------------------------------
CODE : Prefetch
------------------------------------------------------------------------------
for livre in Livre.objects.prefetch_related("categories"):
    for categorie in livre.categories.all():
        print(categorie.nom)
------------------------------------------------------------------------------


[BONNE PRATIQUE]

`select_related` fait une jointure SQL et convient aux clés étrangères et
aux relations un à un. `prefetch_related` exécute une requête séparée et
convient aux relations plusieurs à plusieurs et aux relations inverses.

[/BONNE PRATIQUE]



### Agrégations et annotations


------------------------------------------------------------------------------
CODE : Compter et agréger
------------------------------------------------------------------------------
from django.db.models import Count, Avg

Livre.objects.aggregate(total=Count("id"))
Categorie.objects.annotate(nb_livres=Count("livres"))
------------------------------------------------------------------------------

`aggregate` renvoie un dictionnaire pour l'ensemble du QuerySet.
`annotate` ajoute un attribut calculé à chaque objet.

[A RETENIR]


  - Un modèle décrit une table ; l'ORM traduit Python en SQL.
  - `ForeignKey`, `ManyToManyField` et `OneToOneField` couvrent
    les relations.
  - `on_delete=PROTECT` protège les données liées.
  - `makemigrations` prépare, `migrate` applique.
  - `get`, `filter`, `exclude` et `order_by` forment la
    base des requêtes.
  - `select_related` et `prefetch_related` évitent le problème
    N+1.


[/A RETENIR]

CHAPITRE 8 : GÉRER LES REQUÊTES ET LES VUES
==============================================================================


Une vue reçoit une requête et renvoie une réponse. Dans ce chapitre, vous explorez l'objet `request`, les codes de statut, les raccourcis `redirect` et `get_object_or_404`, les convertisseurs d'URL, la recherche, les filtres et la pagination. Le catalogue de GesiBiblio devient une vraie application qui interroge la base de données.


OBJECTIFS DU CHAPITRE


  - Lire les informations d'une requête HTTP dans l'objet `request`.
  - Choisir le bon type de réponse et le bon code de statut.
  - Utiliser `get_object_or_404`, `redirect` et
    `reverse`.
  - Maîtriser les convertisseurs d'URL et les paramètres nommés.
  - Construire une liste avec recherche, filtre, tri et pagination.
  - Protéger une vue selon la méthode HTTP.
  - Écrire les pages d'erreur 404 et 500.
  - Découvrir les vues basées sur les classes en alternative.



## Le trajet complet d'une requête

Au chapitre précédent, les vues renvoyaient des données écrites à la main. Elles
vont maintenant interroger la base. Le trajet devient complet :


  1. le navigateur envoie une requête `GET /livres/` ;
  2. les middlewares préparent `request` ;
  3. le routeur choisit la vue `livre_liste` ;
  4. la vue interroge les modèles avec l'ORM ;
  5. la base renvoie les lignes ;
  6. la vue transmet un contexte au gabarit ;
  7. le gabarit produit du HTML ;
  8. Django renvoie une `HttpResponse` au navigateur.


[A RETENIR]

Une vue est le chef d'orchestre. Elle ne contient ni HTML ni SQL : elle valide la
requête, interroge les modèles, choisit un gabarit et renvoie une réponse. Cette
séparation rend le code testable et lisible.

[/A RETENIR]



## L'objet request

Django construit un objet `HttpRequest` pour chaque requête. Les attributs
les plus utiles :


Attribut ou méthode | Contenu
`request.method` | Méthode HTTP : `"GET"`, `"POST"`, etc.
`request.GET` | Paramètres de l'URL, après le point d'interrogation.
`request.POST` | Champs du corps, pour un formulaire `POST`.
`request.FILES` | Fichiers téléversés.
`request.path` | Chemin demandé, par exemple `/livres/`.
`request.GET.urlencode` | Paramètres encodés pour construire un lien.
`request.headers` | En-têtes HTTP, insensibles à la casse.
`request.COOKIES` | Cookies envoyés par le navigateur.
`request.user` | Utilisateur connecté, ou `AnonymousUser`.
`request.session` | Données de session.
`request.body` | Corps brut de la requête, en octets.
`request.content_type` | Type de contenu annoncé.
`request.is_secure()` | Vrai si la requête arrive en HTTPS.

Tableau : Les attributs principaux de l'objet request.



### GET et POST


------------------------------------------------------------------------------
CODE : Lire les paramètres
------------------------------------------------------------------------------
def recherche(request):
    mot = request.GET.get("q", "").strip()
    page = request.GET.get("page", "1")
    return render(
        request,
        "catalogue/recherche.html",
        {"mot": mot, "page": page},

------------------------------------------------------------------------------


  - {request.GET["q" : }] Lève `KeyError` si le paramètre manque.
  - `request.GET.get("q")` : Renvoie `None` si le paramètre manque.
  - `request.GET.get("q", "")` : Renvoie une chaîne vide par défaut :
    c'est la forme la plus sûre pour une recherche.
  - `.strip()` : Supprime les espaces autour de la valeur.


[ATTENTION]

Ne faites jamais confiance aux valeurs de `request.GET` ou
`request.POST`. Ce sont des chaînes envoyées par le client. Un utilisateur
peut modifier l'URL, envoyer `page=abc` ou `id=-5`. Validez le type, la
longueur et les valeurs autorisées avant d'utiliser une donnée.

[/ATTENTION]

### Le code de statut


------------------------------------------------------------------------------
CODE : Choisir un statut
------------------------------------------------------------------------------
from django.http import HttpResponse, JsonResponse


def sante(request):
    return JsonResponse({"statut": "ok", "version": "1.0"})


def page_absente(request):
    return HttpResponse(
        "<h1>Contenu introuvable</h1>",

`302` vers la fiche, ou `201` dans une API.

[/BONNE PRATIQUE]



### Rediriger

Après un formulaire validé, on redirige vers une autre URL. Cela évite qu'un
rafraîchissement ne renvoie le formulaire.


------------------------------------------------------------------------------
CODE : Redirection
------------------------------------------------------------------------------
from django.shortcuts import redirect, render
from .models import Livre


def livre_creation_rapide(request):
    if request.method == "POST":
        titre = request.POST.get("titre", "").strip()
        if titre:
            livre = Livre.objects.create(
                titre=titre,
                slug=titre.lower().replace(" ", "-"),
                isbn="9780000000000",
                auteur_id=1,
                annee_publication=2024,
            )
            return redirect(livre)
    return render(request, "catalogue/livres/creation.html")
------------------------------------------------------------------------------


  - `redirect("catalogue:livre_liste")` : Redirige vers une route nommée.
  - `redirect(livre)` : Utilise `livre.get_absolute_url()`.
  - `redirect("/livres/")` : Redirige vers un chemin littéral, à éviter.


[NOTE]

Le motif « POST puis redirection puis GET » s'appelle le patron
Post/Redirect/Get. Il empêche le navigateur de proposer de renvoyer le
formulaire lors d'un rafraîchissement. Nous l'utiliserons systématiquement avec
les formulaires.

[/NOTE]



## Les objets et les 404


------------------------------------------------------------------------------
CODE : Récupérer un objet
------------------------------------------------------------------------------
from django.shortcuts import get_object_or_404, render
from .models import Livre


def livre_detail(request, slug):
    livre = get_object_or_404(
        Livre.objects.select_related("auteur").prefetch_related("categories"),
        slug=slug,
    )
    return render(
        request,
        "catalogue/livres/detail.html",
        {"livre": livre},
    )
------------------------------------------------------------------------------

`get_object_or_404` exécute la requête et lève une `Http404` si aucun
objet ne correspond. Django renvoie alors la page 404, ou la page de débogage en
développement. Sans ce raccourci, il faudrait écrire :


------------------------------------------------------------------------------
CODE : Équivalent sans raccourci
------------------------------------------------------------------------------
from django.http import Http404

try:
    livre = Livre.objects.get(slug=slug)
except Livre.DoesNotExist:
    raise Http404("Ce livre n'existe pas.")
------------------------------------------------------------------------------


[BONNE PRATIQUE]

Utilisez `get_object_or_404` pour toute fiche accessible par URL. Cela
évite une erreur 500 lorsqu'un identifiant n'existe pas et donne au visiteur une
réponse propre. Il existe aussi `get_list_or_404` pour les listes.

[/BONNE PRATIQUE]


[ATTENTION]

`get()` sans filtre unique peut lever `MultipleObjectsReturned`. Un slug
ou un ISBN sont uniques : ce sont de bons paramètres d'URL. N'utilisez pas
`titre` comme identifiant, deux livres peuvent avoir le même titre.

[/ATTENTION]

### reverse et resolve


------------------------------------------------------------------------------
CODE : Construire et analyser une URL
------------------------------------------------------------------------------
from django.urls import resolve, reverse

url = reverse("catalogue:livre_detail", kwargs={"slug": "le-petit-prince"})
# /livres/le-petit-prince/

Dans le code Python, utilisez `reverse`. Dans un gabarit, utilisez
`{% url %}`. Ces deux fonctions construisent les liens à partir du nom
de route et évitent les chemins codés en dur.

[/BONNE PRATIQUE]



## La liste des livres

Nous allons construire une liste complète : recherche, filtre par catégorie, tri et
pagination.



### La vue


------------------------------------------------------------------------------
CODE : catalogue/views.py, extrait
------------------------------------------------------------------------------
from django.core.paginator import Paginator
from django.db.models import Count, Q
from django.shortcuts import get_object_or_404, render

from .models import Auteur, Categorie, Livre

TRI_AUTORISE = {
    "titre": "titre",
    "recent": "-annee_publication",
    "auteur": "auteur__nom",
}


def livre_liste(request):
    livres = (
        Livre.objects.select_related("auteur")
        .prefetch_related("categories")
    )

    mot = request.GET.get("q", "").strip()
    if mot:
        livres = livres.filter(
            Q(titre__icontains=mot)
            | Q(auteur__nom__icontains=mot)
            | Q(isbn__icontains=mot)
        )

    categorie_slug = request.GET.get("categorie", "").strip()
    if categorie_slug:
        livres = livres.filter(categories__slug=categorie_slug)

    tri = request.GET.get("tri", "titre")
    livres = livres.order_by(TRI_AUTORISE.get(tri, "titre"))

    paginator = Paginator(livres, 6)
    page = paginator.get_page(request.GET.get("page"))

    categories = Categorie.objects.annotate(
        nb_livres=Count("livres")
    )

    contexte = {
        "page_obj": page,
        "livres": page.object_list,
        "categories": categories,
        "mot": mot,
        "categorie_active": categorie_slug,
        "tri": tri,
        "nombre_resultats": paginator.count,
    }
    return render(request, "catalogue/livres/liste.html", contexte)
------------------------------------------------------------------------------


[ATTENTION]

Ne confondez pas deux usages du symbole `|`. À l'intérieur d'un
`filter`, `Q(...) | Q(...)` combine des conditions dans la même
requête : c'est la forme recommandée. Entre deux QuerySets,
`queryset1 | queryset2` fusionne deux résultats, ne dédoublonne pas toujours
et empêche parfois d'enchaîner un filtre. Pour une recherche sur plusieurs champs,
utilisez `Q`.

[/ATTENTION]



### Comprendre la pagination


------------------------------------------------------------------------------
CODE : Le Paginator
------------------------------------------------------------------------------
from django.core.paginator import Paginator

paginator = Paginator(Livre.objects.all(), 6)
page = paginator.get_page(3)
------------------------------------------------------------------------------


  - `paginator.count` : Nombre total d'objets.
  - `paginator.num_pages` : Nombre total de pages.
  - `paginator.page_range` : Plage de numéros de page.
  - `page.number` : Numéro de la page courante.
  - `page.object_list` : Objets de la page.
  - `page.has_previous()` : Vrai s'il existe une page avant.
  - `page.has_next()` : Vrai s'il existe une page après.
  - `page.previous_page_number` : Numéro de la page précédente.
  - `page.next_page_number` : Numéro de la page suivante.
  - `paginator.get_page(n)` : Renvoie la page `n`, ou la première ou
    la dernière page si la valeur est invalide. Ne lève pas d'erreur : c'est la
    méthode à utiliser avec un paramètre utilisateur.


[BONNE PRATIQUE]

`get_page()` accepte `None`, une chaîne vide, `"abc"` ou un numéro
hors limites sans lever d'exception. Il renvoie la page appropriée. Préférez-le à
`paginator.page()`, qui lève `EmptyPage` ou `PageNotAnInteger`.

[/BONNE PRATIQUE]

## Protéger une vue selon la méthode HTTP

Certaines actions ne doivent accepter que `POST`. Django fournit des
décorateurs.


------------------------------------------------------------------------------
CODE : Décorateurs de méthode
------------------------------------------------------------------------------
from django.views.decorators.http import (
    require_GET,
    require_POST,
    require_http_methods,
)


@require_GET
def livre_liste(request):
    ...


@require_POST
def livre_supprimer(request, pk):
    ...


@require_http_methods(["GET", "POST"])
def livre_modifier(request, pk):
    ...
------------------------------------------------------------------------------

Si la méthode ne correspond pas, Django renvoie `405 Method Not Allowed`.
C'est plus propre qu'un message maison et plus sûr qu'une suppression déclenchée
par un simple lien.


[ATTENTION]

Ne supprimez jamais une donnée avec un lien `<a href="...">`. Un moteur de
recherche ou un antivirus peut suivre le lien et supprimer vos enregistrements. La
suppression se fait avec un formulaire `POST`, une confirmation et, idéalement,
une vérification de permission.

[/ATTENTION]

## Les vues basées sur les classes

Les vues basées sur les fonctions sont le fil principal de ce module. Django

------------------------------------------------------------------------------

------------------------------------------------------------------------------
from django.views.generic import DetailView, ListView

from .models import Livre


class LivreListView(ListView):
    model = Livre
    template_name = "catalogue/livres/liste.html"
    context_object_name = "livres"
    paginate_by = 6

    template_name = "catalogue/livres/detail.html"
    context_object_name = "livre"

------------------------------------------------------------------------------
CODE : catalogue/urls.py, alternative CBV
------------------------------------------------------------------------------

path("livres/<slug:slug>/", views.LivreDetailView.as_view(), name="livre_detail"),
------------------------------------------------------------------------------


  - `ListView` : Récupère une liste, la pagine et la place dans le
    contexte. Le nom par défaut est `object_list` ; ici, il devient
    `livres` grâce à `context_object_name`.
  - `DetailView` : Récupère un objet à partir de `pk` ou
    `slug`. Le nom par défaut est `object`.
  - `get_queryset()` : Point d'entrée pour filtrer ou optimiser la
    requête.


[BONNE PRATIQUE]

Pour un débutant, les vues basées sur les fonctions sont plus faciles à lire et à
déboguer. Les classes deviennent intéressantes quand vous répétez le même schéma
de liste ou de détail. Ne mélangez pas les deux styles dans une même vue.

[/BONNE PRATIQUE]


[ERREUR FREQUENTE]

Si vous remplacez une vue fonction par une classe, pensez à `.as_view()` dans
`urls.py`. Sans cela, Django reçoit une classe et non une fonction : vous
obtenez une erreur `TypeError` ou un comportement inattendu.

[/ERREUR FREQUENTE]

==============================================================================
CHAPITRE 9 : L'ADMINISTRATION DJANGO
==============================================================================


Django fournit une interface d'administration complète, accessible sans écrire de HTML. Dans ce chapitre, vous créez un superutilisateur, vous enregistrez les modèles du catalogue, vous personnalisez les listes, les filtres et les formulaires, puis vous ajoutez des actions de masse et une identité visuelle à l'interface.


OBJECTIFS DU CHAPITRE


  - Créer un superutilisateur et se connecter à l'administration.
  - Enregistrer un modèle avec `admin.site.register`.
  - Personnaliser une liste avec `ModelAdmin`.
  - Ajouter des filtres, une recherche, un ordre et une hiérarchie de dates.
  - Utiliser les inlines pour éditer les objets liés.
  - Écrire une action personnalisée.
  - Personnaliser le titre et l'en-tête de l'administration.
  - Comprendre les limites de sécurité de l'administration.



## À quoi sert l'administration ?

L'administration est une application fournie par Django. Elle lit vos modèles et
génère automatiquement des écrans de liste, de création, de modification et de
suppression. Pour un projet de gestion, c'est un gain de temps considérable : les
bibliothécaires peuvent gérer le catalogue avant même que le site public ne soit
terminé.


[A RETENIR]

L'administration n'est pas le site public. C'est un outil interne, réservé aux
personnes autorisées. Les bibliothécaires y ajoutent des livres, corrigent des
fiches et enregistrent des retours. Les lecteurs, eux, utilisent les pages
publiques.

[/A RETENIR]

L'application d'administration fait partie des applications installées par
défaut. Sa route est déjà branchée dans le fichier d'URL du projet :


------------------------------------------------------------------------------
CODE : gesibiblio/urls.py, extrait
------------------------------------------------------------------------------
path("admin/", admin.site.urls),
------------------------------------------------------------------------------



## Créer un superutilisateur


TERMINAL :
  $ python manage.py createsuperuser

Django demande un nom d'utilisateur, une adresse électronique et un mot de passe.
Le mot de passe n'est pas affiché pendant la saisie. Sortie typique :


TERMINAL :
  $ Nom d'utilisateur : admin
  $ Adresse électronique : admin@gesibiblio.example
  $ Password :
  $ Password (again) :
  $ Superuser created successfully.

Lancez le serveur, puis ouvrez `http://127.0.0.1:8000/admin/`.


[ATTENTION]

Un superutilisateur a tous les droits. Ne partagez pas ce compte, ne le créez pas
avec le mot de passe `admin` et ne le laissez pas accessible en production
sans HTTPS. Pour le développement local, un compte simple suffit.

[/ATTENTION]

Au premier démarrage, l'administration ne montre que les groupes et les
utilisateurs. Nos modèles n'apparaissent pas encore : il faut les enregistrer.

## Personnaliser l'affichage

`admin.site.register(Livre)` suffit pour démarrer, mais la liste par défaut
affiche seulement `__str__`. Pour un vrai usage, on déclare une classe
`ModelAdmin`.


------------------------------------------------------------------------------
CODE : catalogue/admin.py
------------------------------------------------------------------------------
from django.contrib import admin

from .models import Auteur, Categorie, Emprunt, Livre, Membre


@admin.register(Auteur)
class AuteurAdmin(admin.ModelAdmin):
    list_display = ("nom", "prenom", "date_naissance", "nb_livres")
    search_fields = ("nom", "prenom")
    ordering = ("nom", "prenom")

    @admin.display(description="Livres")
    def nb_livres(self, obj):
        return obj.livres.count()


@admin.register(Categorie)
class CategorieAdmin(admin.ModelAdmin):
    list_display = ("nom", "slug", "nb_livres")
    search_fields = ("nom",)
    prepopulated_fields = {"slug": ("nom",)}

    @admin.display(description="Livres")
    def nb_livres(self, obj):
        return obj.livres.count()


@admin.register(Livre)
class LivreAdmin(admin.ModelAdmin):
    list_display = (
        "titre",
        "auteur",
        "annee_publication",
        "statut",
        "nombre_exemplaires",
    )
    list_filter = ("statut", "categories", "annee_publication")
    search_fields = ("titre", "isbn", "auteur__nom")
    list_select_related = ("auteur",)
    date_hierarchy = "cree_le"
    ordering = ("titre",)
    readonly_fields = ("cree_le", "modifie_le")
    autocomplete_fields = ("auteur", "categories")
    fieldsets = (
        ("Identification", {
            "fields": ("titre", "sous_titre", "slug", "isbn"),
        }),
        ("Publication", {
            "fields": (
                "auteur",
                "editeur",
                "annee_publication",
                "categories",
            ),
        }),
        ("Stock", {
            "fields": ("nombre_exemplaires", "statut", "couverture"),
        }),
        ("Contenu", {
            "fields": ("resume",),
        }),
        ("Suivi", {
            "fields": ("cree_le", "modifie_le"),
            "classes": ("collapse",),
        }),
    )


@admin.register(Membre)
class MembreAdmin(admin.ModelAdmin):
    list_display = ("numero", "user", "telephone", "actif", "date_inscription")
    list_filter = ("actif",)
    search_fields = ("numero", "user__username", "user__last_name")
    autocomplete_fields = ("user",)
    date_hierarchy = "date_inscription"


@admin.register(Emprunt)
class EmpruntAdmin(admin.ModelAdmin):
    list_display = (
        "livre",
        "membre",
        "date_emprunt",
        "date_retour_prevue",
        "rendu",
        "retard",
    )
    list_filter = ("date_emprunt", "date_retour_prevue")
    search_fields = ("livre__titre", "membre__numero")
    list_select_related = ("livre", "membre")
    date_hierarchy = "date_emprunt"
    autocomplete_fields = ("livre", "membre")

    @admin.display(boolean=True, description="Rendu")
    def rendu(self, obj):
        return obj.date_retour is not None

    @admin.display(boolean=True, description="En retard")
    def retard(self, obj):
        return obj.est_en_retard
------------------------------------------------------------------------------


[ATTENTION]

`autocomplete_fields` exige que le modèle cible possède un
`search_fields` dans son `ModelAdmin`. Pour `livre` et
`membre`, c'est le cas. Pour `user`, il faut enregistrer un
`UserAdmin` personnalisé ou retirer `user` de
`autocomplete_fields`.

[/ATTENTION]



### Les options de liste


Option | Effet
`list_display` | Colonnes affichées. Accepte des noms de champs, des
méthodes et des propriétés.
`list_filter` | Filtres dans la barre latérale droite.
`search_fields` | Champs interrogés par la recherche.
`list_select_related` | Charge les clés étrangères en une requête.
`list_per_page` | Nombre d'objets par page.
`ordering` | Ordre par défaut de la liste.
`date_hierarchy` | Navigation par année, mois et jour.
`list_editable` | Modifie un champ directement dans la liste.
`list_display_links` | Champs cliquables vers la fiche.

Tableau : Options principales d'une liste d'administration.


[BONNE PRATIQUE]

Ajoutez `list_select_related` dès que `list_display` contient une clé
étrangère. Sans cela, Django exécute une requête par ligne pour afficher l'auteur
de chaque livre. Sur 500 livres, cela fait 501 requêtes.

[/BONNE PRATIQUE]



### Les colonnes calculées


------------------------------------------------------------------------------
CODE : Colonne avec décorateur
------------------------------------------------------------------------------
@admin.display(description="Livres", ordering="livres__count")
def nb_livres(self, obj):
    return obj.livres.count()
------------------------------------------------------------------------------


  - `description` : Titre de la colonne.
  - `boolean` : Affiche une icône verte ou rouge.
  - `ordering` : Permet de trier la colonne. Pour un comptage, la valeur
    doit être une expression acceptée par l'ORM, souvent une annotation.


[NOTE]

Une colonne calculée avec `obj.livres.count()` déclenche une requête par
ligne. Pour une liste volumineuse, annotez le queryset dans
`get_queryset()` avec `Count("livres")` et lisez l'attribut ajouté.

[/NOTE]



## Les formulaires d'administration



### fieldsets

`fieldsets` regroupe les champs en sections. Chaque section est un couple
« titre, dictionnaire ». Le dictionnaire contient `fields` et
éventuellement `classes` (`collapse`, `wide`).


------------------------------------------------------------------------------
CODE : fieldsets, extrait
------------------------------------------------------------------------------
fieldsets = (
    ("Identification", {
        "fields": ("titre", "isbn"),
    }),
    ("Détails", {
        "fields": ("auteur", "annee_publication"),
        "classes": ("collapse",),
    }),
)
------------------------------------------------------------------------------


[ATTENTION]

Si vous utilisez `fieldsets`, tous les champs éditables doivent y figurer.
Un champ oublié disparaît du formulaire et devient impossible à modifier. Les
champs `readonly_fields` doivent aussi être listés.

[/ATTENTION]



### prepopulated_fields


------------------------------------------------------------------------------
CODE : Slug automatique
------------------------------------------------------------------------------
prepopulated_fields = {"slug": ("titre",)}
------------------------------------------------------------------------------

Le slug se remplit pendant la saisie du titre, en JavaScript. L'utilisateur peut le
corriger. C'est un confort, pas une validation : le modèle garde
`unique=True`.



### Les inlines

Un emprunt appartient à un livre et à un membre. Pour voir les emprunts d'un livre
directement dans sa fiche, on utilise un inline.


------------------------------------------------------------------------------
CODE : Inline d'emprunts
------------------------------------------------------------------------------
class EmpruntInline(admin.TabularInline):
    model = Emprunt
    extra = 1
    fields = ("membre", "date_emprunt", "date_retour_prevue", "date_retour")
    autocomplete_fields = ("membre",)


@admin.register(Livre)
class LivreAdmin(admin.ModelAdmin):
    # ... options existantes
    inlines = [EmpruntInline]
------------------------------------------------------------------------------


  - `TabularInline` : Tableau compact, adapté aux relations simples.
  - `StackedInline` : Formulaire vertical, adapté aux objets riches.
  - `extra` : Nombre de lignes vides proposées.
  - `can_delete` : Autorise la suppression des lignes liées.


[ATTENTION]

Un inline ne fonctionne que si la clé étrangère pointe vers le modèle parent. Ici,
`Emprunt.livre` pointe vers `Livre`. Pour une relation
plusieurs à plusieurs, utilisez `filter_horizontal` ou
`autocomplete_fields`, pas un inline.

[/ATTENTION]



## Les actions de masse

Une action s'applique à plusieurs objets sélectionnés. Exemple : marquer des livres
comme perdus, ou exporter une sélection en CSV.


------------------------------------------------------------------------------
CODE : catalogue/admin.py, extrait
------------------------------------------------------------------------------
import csv

from django.http import HttpResponse


@admin.action(description="Marquer les livres sélectionnés comme perdus")
def marquer_perdus(modeladmin, request, queryset):
    nombre = queryset.update(statut=Livre.Statut.PERDU)
    modeladmin.message_user(
        request,
        f"{nombre} livre(s) marqué(s) comme perdus.",
    )


@admin.action(description="Exporter la sélection en CSV")
def exporter_csv(modeladmin, request, queryset):
    response = HttpResponse(content_type="text/csv")
    response["Content-Disposition"] = 'attachment; filename="livres.csv"'
    writer = csv.writer(response)
    writer.writerow(["Titre", "Auteur", "ISBN", "Année", "Statut"])
    for livre in queryset.select_related("auteur"):
        writer.writerow([
            livre.titre,
            livre.auteur,
            livre.isbn,
            livre.annee_publication,
            livre.get_statut_display(),
        ])
    return response


@admin.register(Livre)
class LivreAdmin(admin.ModelAdmin):
    # ... options existantes
    actions = [marquer_perdus, exporter_csv]
------------------------------------------------------------------------------


[BONNE PRATIQUE]

Les actions doivent être idempotentes autant que possible : les exécuter deux fois
ne doit pas produire de dégât. Affichez toujours un message avec
`message_user` pour indiquer ce qui a été fait. Pour une action destructrice,
ajoutez une page de confirmation.

[/BONNE PRATIQUE]


[ERREUR FREQUENTE]

Une action qui renvoie `None` recharge la liste. Une action qui renvoie une
`HttpResponse` affiche cette réponse : c'est ce que fait l'export CSV. Si
vous oubliez de renvoyer la réponse, le fichier n'est jamais téléchargé.

[/ERREUR FREQUENTE]

## Sécurité de l'administration

L'administration est puissante. Quelques règles :


[BONNE PRATIQUE]


  - utiliser HTTPS en production ;
  - changer l'URL `/admin/` par un chemin moins évident, sans compter
    sur le secret ;
  - limiter les comptes `is_superuser` ;
  - donner aux bibliothécaires des permissions précises plutôt qu'un statut
    global ;
  - activer la double authentification si l'infrastructure le permet ;
  - sauvegarder la base avant toute opération de masse.


[/BONNE PRATIQUE]


[ATTENTION]

Changer l'URL de l'administration ne remplace pas les permissions. Un attaquant
peut découvrir le chemin. La vraie protection repose sur des mots de passe solides,
HTTPS, des droits limités et une surveillance des connexions.

[/ATTENTION]

from django.utils import timezone


class EmpruntEnRetardFilter(admin.SimpleListFilter):
    title = "emprunts en retard"
    parameter_name = "retard"

    def lookups(self, request, model_admin):
        return (
            ("oui", "En retard"),
            ("non", "À jour"),
        )

    def queryset(self, request, queryset):
        aujourdhui = timezone.localdate()
        if self.value() == "oui":
            return queryset.filter(
                date_retour__isnull=True,
                date_retour_prevue__lt=aujourdhui,
            )
        if self.value() == "non":
            return queryset.filter(
                date_retour__isnull=True,
                date_retour_prevue__gte=aujourdhui,
            )
        return queryset

==============================================================================
CHAPITRE 10 : LES FORMULAIRES DJANGO
==============================================================================


Un catalogue sans saisie serait bien triste. Dans ce chapitre, vous créez des formulaires capables de valider les données, de téléverser une couverture et d'enregistrer un emprunt. Vous découvrez `forms.Form`, `ModelForm`, la validation personnalisée, les messages et les vues de création, de modification et de suppression.


OBJECTIFS DU CHAPITRE


  - Distinguer un formulaire HTML d'un formulaire Django.
  - Écrire un `forms.Form` et un `ModelForm`.
  - Afficher un formulaire dans un gabarit et gérer les erreurs.
  - Traiter une requête `POST` avec `csrf_token`.
  - Valider un emprunt avec `clean()` et `clean_<champ>()`.
  - Téléverser une image de couverture.
  - Afficher des messages flash après une action.
  - Écrire les vues de création, de modification et de suppression.
  - Découvrir `CreateView` et `UpdateView` en alternative.



## Pourquoi un formulaire Django ?

Un formulaire HTML envoie des chaînes. Il faut ensuite vérifier que le titre n'est
pas vide, que l'ISBN contient treize chiffres, que l'année est plausible, que
l'auteur existe. Django centralise ces vérifications dans une classe Python.


[A RETENIR]

Un formulaire Django fait trois choses : il génère le HTML, il valide les données et
il nettoie les valeurs. La vue n'a plus qu'à tester `form.is_valid()` et à
enregistrer. C'est plus sûr et plus lisible qu'une série de `if` dans le
gabarit.

[/A RETENIR]



## Un premier formulaire


------------------------------------------------------------------------------
CODE : catalogue/forms.py
------------------------------------------------------------------------------
from django import forms


class ContactForm(forms.Form):
    nom = forms.CharField(
        max_length=80,
        label="Votre nom",
    )
    email = forms.EmailField(label="Votre adresse électronique")
    message = forms.CharField(
        label="Message",
        widget=forms.Textarea(attrs={"rows": 5}),
    )
    copie = forms.BooleanField(
        label="Recevoir une copie",
        required=False,
    )
------------------------------------------------------------------------------


  - `CharField` : Texte court. `max_length` est obligatoire pour la
    validation.
  - `EmailField` : Vérifie le format de l'adresse.
  - `BooleanField` : Case à cocher. `required=False` la rend
    facultative.
  - `label` : Texte affiché devant le champ.
  - `widget` : Contrôle HTML utilisé. `Textarea` pour un texte long.

## Le ModelForm

Un `ModelForm` construit le formulaire à partir d'un modèle. Il crée, valide et
enregistre les données sans répéter les champs.


------------------------------------------------------------------------------
CODE : catalogue/forms.py, extrait
------------------------------------------------------------------------------
from django import forms

from .models import Livre


class LivreForm(forms.ModelForm):
    class Meta:
        model = Livre
        fields = [
            "titre",
            "sous_titre",
            "slug",
            "isbn",
            "auteur",
            "categories",
            "editeur",
            "annee_publication",
            "nombre_exemplaires",
            "couverture",
            "resume",
            "statut",
        ]
        widgets = {
            "resume": forms.Textarea(attrs={"rows": 6}),
            "sous_titre": forms.TextInput(attrs={"placeholder": "Facultatif"}),
            "couverture": forms.ClearableFileInput(attrs={"accept": "image/*"}),
        }
        labels = {
            "isbn": "ISBN (13 chiffres)",
            "annee_publication": "Année de publication",
        }
        help_texts = {
            "slug": "Identifiant lisible utilisé dans l'URL.",
            "nombre_exemplaires": "Nombre total d'exemplaires possédés.",
        }
------------------------------------------------------------------------------


[ATTENTION]

N'utilisez jamais `fields = "__all__"` sans réfléchir. Un champ ajouté plus
tard au modèle apparaîtrait automatiquement dans le formulaire, y compris un champ
sensible comme `actif` ou `proprietaire`. Listez explicitement les champs
que l'utilisateur a le droit de modifier.

[/ATTENTION]

## Valider un emprunt

Un emprunt doit respecter des règles métier :

  - le livre doit être disponible ;
  - la date de retour prévue doit être postérieure à la date d'emprunt ;
  - le membre doit être actif ;
  - un membre ne peut pas emprunter deux fois le même livre en cours.


[FIGURE] Le cycle de vie d'un emprunt, de la demande au retour. Les règles de validation protègent chaque transition.



------------------------------------------------------------------------------
CODE : catalogue/forms.py, extrait
------------------------------------------------------------------------------
from django import forms
from django.utils import timezone

from .models import Emprunt


class EmpruntForm(forms.ModelForm):
    class Meta:
        model = Emprunt
        fields = ["livre", "membre", "date_retour_prevue", "remarque"]
        widgets = {
            "date_retour_prevue": forms.DateInput(attrs={"type": "date"}),
            "remarque": forms.Textarea(attrs={"rows": 3}),
        }

    def clean_date_retour_prevue(self):
        date_prevue = self.cleaned_data["date_retour_prevue"]
        if date_prevue < timezone.localdate():
            raise forms.ValidationError(
                "La date de retour ne peut pas être dans le passé."
            )
        return date_prevue

    def clean(self):
        donnees = super().clean()
        livre = donnees.get("livre")
        membre = donnees.get("membre")

        if livre and not livre.est_disponible:
            self.add_error(
                "livre",
                "Ce livre n'est pas disponible pour le moment.",
            )

        if membre and not membre.actif:
            self.add_error(
                "membre",
                "Ce membre est inactif et ne peut pas emprunter.",
            )

        if livre and membre:
            deja = Emprunt.objects.filter(
                livre=livre,
                membre=membre,
                date_retour__isnull=True,
            )
            if self.instance.pk:
                deja = deja.exclude(pk=self.instance.pk)
            if deja.exists():
                raise forms.ValidationError(
                    "Ce membre a déjà un emprunt en cours pour ce livre."
                )

        return donnees
------------------------------------------------------------------------------


  - `clean_<champ>()` : Valide un champ précis. La valeur renvoyée remplace
    celle de `cleaned_data`.
  - `clean()` : Validation globale, après les champs individuels.
  - `add_error("champ", ...)` : Attache l'erreur au champ concerné.
  - `ValidationError` : Erreur générale, affichée dans
    `non_field_errors`.


[BONNE PRATIQUE]

Les règles métier vont dans le formulaire ou dans le modèle, pas dans le gabarit.
Un formulaire peut être testé sans navigateur, avec
`EmpruntForm(data=...)`. C'est rapide et fiable.

[/BONNE PRATIQUE]


[ERREUR FREQUENTE]

Dans `clean()`, utilisez `donnees.get("livre")` et non
`donnees["livre"]`. Si le champ a déjà échoué, la clé est absente et vous
provoquez une `KeyError` au lieu d'afficher l'erreur principale.

[/ERREUR FREQUENTE]

### Enregistrer un retour

Le retour n'est pas une modification libre : c'est une action datée.


------------------------------------------------------------------------------
CODE : catalogue/views.py, extrait
------------------------------------------------------------------------------
from django.utils import timezone
from django.views.decorators.http import require_POST


@require_POST
def emprunt_retour(request, pk):
    emprunt = get_object_or_404(Emprunt, pk=pk)
    if emprunt.date_retour is None:
        emprunt.date_retour = timezone.localdate()
        emprunt.save(update_fields=["date_retour"])
        messages.success(request, "Le retour a été enregistré.")
    else:
        messages.info(request, "Ce livre a déjà été rendu.")
    return redirect("catalogue:emprunt_liste")
------------------------------------------------------------------------------


[NOTE]

`update_fields` limite la requête `UPDATE` aux colonnes indiquées. C'est
plus rapide et cela évite d'écraser une modification concurrente sur un autre
champ. Utilisez-le quand vous modifiez un seul champ.

[/NOTE]



## Recherche et formulaire GET

Un formulaire de recherche ne modifie rien : il utilise `GET`. Les paramètres
apparaissent dans l'URL, ce qui permet de partager un lien.


------------------------------------------------------------------------------
CODE : catalogue/forms.py, extrait
------------------------------------------------------------------------------
class RechercheLivreForm(forms.Form):
    q = forms.CharField(
        required=False,
        label="Rechercher",
        widget=forms.TextInput(
            attrs={"type": "search", "placeholder": "Titre ou auteur"}
        ),
    )
    categorie = forms.ModelChoiceField(
        queryset=None,
        required=False,
        empty_label="Toutes les catégories",
    )
    tri = forms.ChoiceField(
        required=False,
        choices=[
            ("titre", "Titre"),
            ("recent", "Année décroissante"),
            ("auteur", "Auteur"),
        ],
    )

    def __init__(self, *args, **kwargs):
        super().__init__(*args, **kwargs)
        from .models import Categorie

        self.fields["categorie"].queryset = Categorie.objects.all()
------------------------------------------------------------------------------


[ATTENTION]

Un `ModelChoiceField` exécute une requête pour construire ses options. Définir
le queryset dans `__init__` plutôt qu'au niveau de la classe évite une
requête au moment de l'import du module et permet de filtrer selon l'utilisateur.

[/ATTENTION]


------------------------------------------------------------------------------
CODE : Vue avec formulaire GET
------------------------------------------------------------------------------
def livre_liste(request):
    form = RechercheLivreForm(request.GET or None)
    livres = Livre.objects.select_related("auteur")

    if form.is_valid():
        mot = form.cleaned_data.get("q")
        categorie = form.cleaned_data.get("categorie")
        tri = form.cleaned_data.get("tri") or "titre"

        if mot:
            livres = livres.filter(titre__icontains=mot)
        if categorie:
            livres = livres.filter(categories=categorie)

        livres = livres.order_by(tri)

    return render(
        request,
        "catalogue/livres/liste.html",
        {"form": form, "livres": livres},
    )
------------------------------------------------------------------------------


[NOTE]

Avec `request.GET or None`, un premier appel sans paramètre donne
`None`, donc un formulaire non lié, sans erreurs. Un appel avec `?q=`
donne un formulaire lié, valide, avec une recherche vide. C'est le comportement
attendu.

[/NOTE]

## Les vues génériques de formulaire

Comme pour les listes, Django propose des classes.


------------------------------------------------------------------------------
CODE : catalogue/views.py, alternative CBV
------------------------------------------------------------------------------
from django.urls import reverse_lazy
from django.views.generic import CreateView, DeleteView, UpdateView

from .forms import LivreForm
from .models import Livre


class LivreCreateView(CreateView):
    model = Livre
    form_class = LivreForm
    template_name = "catalogue/livres/formulaire.html"

    def get_context_data(self, **kwargs):
        contexte = super().get_context_data(**kwargs)
        contexte["titre_page"] = "Ajouter un livre"
        return contexte


class LivreUpdateView(UpdateView):
    model = Livre
    form_class = LivreForm
    template_name = "catalogue/livres/formulaire.html"


class LivreDeleteView(DeleteView):
    model = Livre
    template_name = "catalogue/livres/supprimer.html"
    success_url = reverse_lazy("catalogue:livre_liste")
------------------------------------------------------------------------------


  - `CreateView` : Affiche le formulaire en `GET`, enregistre en
    `POST` valide, puis redirige vers `get_absolute_url()`.
  - `UpdateView` : Même principe, avec un objet existant.
  - `DeleteView` : Affiche une confirmation en `GET`, supprime en
    `POST`.
  - `success_url` : Utilise `reverse_lazy` pour éviter un import
    circulaire.


[ERREUR FREQUENTE]

`reverse_lazy` est nécessaire dans un attribut de classe évalué à l'import.
`reverse` y serait exécuté trop tôt, avant que les URL ne soient chargées, et
provoquerait une `NoReverseMatch`.

[/ERREUR FREQUENTE]

============================================================
EXERCICE : prolonger un emprunt
============================================================

Écrivez une vue `emprunt_prolonger` qui ajoute quatorze jours à
`date_retour_prevue`, uniquement si l'emprunt n'est pas rendu et si le
membre est actif.


[CORRECTION]


------------------------------------------------------------------------------
CODE : catalogue/views.py, extrait
------------------------------------------------------------------------------
from datetime import timedelta

from django.views.decorators.http import require_POST


@require_POST
def emprunt_prolonger(request, pk):
    emprunt = get_object_or_404(Emprunt, pk=pk)

    if emprunt.date_retour is not None:
        messages.error(request, "Cet emprunt est déjà terminé.")
    elif not emprunt.membre.actif:
        messages.error(request, "Le membre est inactif.")
    else:
        emprunt.date_retour_prevue += timedelta(days=14)
        emprunt.save(update_fields=["date_retour_prevue"])
        messages.success(request, "L'emprunt a été prolongé de 14 jours.")

    return redirect("catalogue:emprunt_liste")
------------------------------------------------------------------------------

`timedelta(days=14)` ajoute quatorze jours à une date. La vue est protégée
par `require_POST` : la prolongation ne peut pas être déclenchée par un lien.

[/CORRECTION]


[A RETENIR]


  - Un formulaire Django génère, valide et nettoie les données.
  - `ModelForm` évite de répéter les champs du modèle.
  - `request.FILES` et `enctype` sont obligatoires pour un fichier.
  - `clean_<champ>()` valide un champ, `clean()` valide l'ensemble.
  - `commit=False` permet d'ajouter une valeur avant l'enregistrement.
  - Après un `POST` réussi, redirigez pour éviter le double envoi.
  - `CreateView`, `UpdateView` et `DeleteView` sont des
    alternatives concises aux vues fonction.


[/A RETENIR]



==============================================================================
CHAPITRE 11 : L'AUTHENTIFICATION DES UTILISATEURS
==============================================================================


Un catalogue public se consulte sans compte. Mais emprunter un livre, réserver un ouvrage ou accéder à son historique demande une identité. Dans ce chapitre, vous utilisez le système d'authentification de Django : inscription, connexion, déconnexion, profil, protection des pages et gestion des sessions.


OBJECTIFS DU CHAPITRE


  - Comprendre le modèle `User` fourni par Django.
  - Activer les URL d'authentification intégrées.
  - Créer les gabarits de connexion et de déconnexion.
  - Écrire un formulaire d'inscription relié au profil `Membre`.
  - Utiliser `login_required` et `LoginRequiredMixin`.
  - Rediriger l'utilisateur vers la page demandée après connexion.
  - Configurer les sessions et les mots de passe.
  - Afficher le profil et l'historique des emprunts.



## Le système d'authentification de Django

Django fournit l'application `django.contrib.auth`, déjà présente dans
`INSTALLED_APPS`. Elle gère :

  - les utilisateurs, avec `User` ;
  - les mots de passe, hachés avec PBKDF2 par défaut ;
  - les sessions, stockées en base ;
  - les groupes et les permissions ;
  - les vues de connexion, de déconnexion et de réinitialisation.


[A RETENIR]

Django ne stocke jamais un mot de passe en clair. Il enregistre une empreinte
calculée avec un sel. La vérification recalcule l'empreinte et compare. Même un
administrateur de la base ne peut pas lire le mot de passe d'origine.

[/A RETENIR]



### Le modèle User


Champ | Rôle
`username` | Identifiant unique. Obligatoire par défaut.
`password` | Empreinte du mot de passe, jamais le mot de passe.
`email` | Adresse électronique, non unique par défaut.
`first_name` | Prénom.
`last_name` | Nom.
`is_active` | Compte autorisé à se connecter.
`is_staff` | Accès à l'administration.
`is_superuser` | Tous les droits.
`date_joined` | Date de création du compte.
`last_login` | Dernière connexion réussie.

Tableau : Les champs principaux du modèle User.


[NOTE]

Pour un nouveau projet, Django recommande un modèle utilisateur personnalisé défini
avant la première migration. Dans ce module, nous gardons le modèle standard : il
suffit pour apprendre et pour le projet GesiBiblio. Le profil `Membre` ajoute
les informations propres à la bibliothèque.

[/NOTE]



## Activer les URL d'authentification

Django fournit un jeu de vues prêt à l'emploi. Ajoutez cette ligne dans
`gesibiblio/urls.py` :


------------------------------------------------------------------------------
CODE : gesibiblio/urls.py
------------------------------------------------------------------------------
from django.contrib import admin
from django.contrib.auth import views as auth_views
from django.urls import include, path

urlpatterns = [
    path("admin/", admin.site.urls),
    path("comptes/", include("django.contrib.auth.urls")),
    path("", include("catalogue.urls")),
]
------------------------------------------------------------------------------


[NOTE]

`django.contrib.auth.urls` n'est pas un module de vues : c'est une liste
d'URL. L'import `auth_views` n'est utile que si vous personnalisez une vue.
Vous pouvez retirer la ligne d'import dans la version minimale.

[/NOTE]

Les routes créées sont :


URL | Nom | Rôle
/comptes/login/ | `login` | Connexion.
/comptes/logout/ | `logout` | Déconnexion.
/comptes/password_change/ | `password_change` | Changement de mot de
passe.
/comptes/password_reset/ | `password_reset` | Demande de
réinitialisation.
/comptes/password_reset/done/ | `password_reset_done` | Confirmation
d'envoi.
/comptes/password_reset/<uidb64>/<token>/ |
`password_reset_confirm` | Saisie du nouveau mot de passe.
/comptes/password_reset/complete/ | `password_reset_complete` |
Succès.

Tableau : URL d'authentification fournies par Django.


[ATTENTION]

Sans les gabarits correspondants, ces URL provoquent une erreur
`TemplateDoesNotExist`. Django cherche les fichiers dans
`registration/` : `registration/login.html`,
`registration/logged_out.html`, etc.

[/ATTENTION]

## Les réglages d'authentification

Ajoutez ces lignes dans `settings.py` :


------------------------------------------------------------------------------
CODE : gesibiblio/settings.py, extrait
------------------------------------------------------------------------------
LOGIN_URL = "login"
LOGIN_REDIRECT_URL = "catalogue:profil"
LOGOUT_REDIRECT_URL = "catalogue:accueil"
------------------------------------------------------------------------------


  - `LOGIN_URL` : Nom de la route de connexion. Utilisé par
    `login_required` pour construire `/comptes/login/?next=...`.
  - `LOGIN_REDIRECT_URL` : Page d'arrivée après connexion, si aucun
    paramètre `next` n'est fourni.
  - `LOGOUT_REDIRECT_URL` : Page d'arrivée après déconnexion.


[NOTE]

Les valeurs sont des noms de route, pas des chemins. Django accepte aussi un chemin
littéral, mais le nom résiste aux changements d'URL. Pour une route d'application,
utilisez le nom complet `catalogue:profil`.

[/NOTE]



## Inscription et profil Membre

Le modèle `Membre` est lié à `User` par une relation un à un. À
l'inscription, il faut créer les deux objets.



### Le formulaire d'inscription


------------------------------------------------------------------------------
CODE : catalogue/forms.py, extrait
------------------------------------------------------------------------------
from django import forms
from django.contrib.auth.forms import UserCreationForm
from django.contrib.auth.models import User


class InscriptionForm(UserCreationForm):
    email = forms.EmailField(
        required=True,
        label="Adresse électronique",
    )
    first_name = forms.CharField(
        max_length=80,
        required=True,
        label="Prénom",
    )
    last_name = forms.CharField(
        max_length=80,
        required=True,
        label="Nom",
    )
    telephone = forms.CharField(
        max_length=20,
        required=False,
        label="Téléphone",
    )

    class Meta(UserCreationForm.Meta):
        model = User
        fields = (
            "username",
            "first_name",
            "last_name",
            "email",
        )

    def clean_email(self):
        email = self.cleaned_data["email"].lower()
        if User.objects.filter(email__iexact=email).exists():
            raise forms.ValidationError(
                "Un compte utilise déjà cette adresse électronique."
            )
        return email
------------------------------------------------------------------------------


  - `UserCreationForm` : Fournit les champs `username`,
    `password1` et `password2`, ainsi que la vérification de
    correspondance.
  - `clean_email()` : Ajoute une unicité que le modèle `User`
    n'impose pas.
  - `lower()` : Normalise l'adresse pour éviter les doublons de casse.



### La vue d'inscription


------------------------------------------------------------------------------
CODE : catalogue/views.py, extrait
------------------------------------------------------------------------------
from django.contrib import messages
from django.contrib.auth import login
from django.shortcuts import redirect, render

from .forms import InscriptionForm
from .models import Membre


def inscription(request):
    if request.method == "POST":
        form = InscriptionForm(request.POST)
        if form.is_valid():
            user = form.save()
            Membre.objects.create(
                user=user,
                numero=f"M{user.pk:05d}",
                telephone=form.cleaned_data.get("telephone", ""),
            )
            login(request, user)
            messages.success(
                request,
                "Bienvenue ! Votre compte membre est créé.",
            )
            return redirect("catalogue:profil")
    else:
        form = InscriptionForm()

    return render(
        request,
        "catalogue/inscription.html",
        {"form": form},
    )
------------------------------------------------------------------------------


  - `form.save()` : Crée l'utilisateur et hache le mot de passe.
  - `Membre.objects.create` : Crée le profil lié, avec un numéro
    `M00042`.
  - `login(request, user)` : Ouvre la session immédiatement après
    l'inscription.
  - {f"M{user.pk:05d}"} : Formate l'identifiant sur cinq chiffres.


[ATTENTION]

La création de l'utilisateur et celle du profil devraient être atomiques. Si la
création du `Membre` échoue, l'utilisateur reste sans profil. Entourez les deux
opérations d'un bloc `transaction.atomic()` :

[/ATTENTION]


------------------------------------------------------------------------------
CODE : Création atomique
------------------------------------------------------------------------------
from django.db import transaction

with transaction.atomic():
    user = form.save()
    Membre.objects.create(
        user=user,
        numero=f"M{user.pk:05d}",
    )
------------------------------------------------------------------------------

[/NOTE]



### La page de profil


------------------------------------------------------------------------------
CODE : catalogue/views.py, extrait
------------------------------------------------------------------------------
from django.contrib.auth.decorators import login_required
from django.shortcuts import get_object_or_404, render

from .models import Membre


@login_required
def profil(request):
    membre = get_object_or_404(Membre, user=request.user)
    emprunts = (
        membre.emprunts.select_related("livre")
        .order_by("-date_emprunt")
    )
    return render(
        request,
        "catalogue/profil.html",
        {"membre": membre, "emprunts": emprunts},
    )
------------------------------------------------------------------------------

[ATTENTION]

`get_object_or_404(Membre, user=request.user)` suppose que chaque
utilisateur a un profil. Un superutilisateur créé avec `createsuperuser` n'en
a pas. Soit vous créez le profil automatiquement, soit vous gérez l'absence avec
`hasattr(request.user, "membre")`.

[/ATTENTION]



## Protéger une vue



### Le décorateur login_required


------------------------------------------------------------------------------
CODE : Protéger une vue fonction
------------------------------------------------------------------------------
from django.contrib.auth.decorators import login_required


@login_required
def profil(request):
    ...
------------------------------------------------------------------------------

Si l'utilisateur n'est pas connecté, Django le redirige vers
`LOGIN_URL` avec `?next=/comptes/profil/`. Après connexion, la vue
`LoginView` lit `next` et renvoie l'utilisateur à la page demandée.


[ATTENTION]

Ne faites pas confiance à `next` sans contrôle. Django fournit
`django.utils.http.url_has_allowed_host_and_scheme` pour éviter une
redirection ouverte vers un site externe. Les vues intégrées appliquent déjà cette
vérification. Si vous écrivez votre propre redirection, faites de même.

[/ATTENTION]



### Le mixin des vues de classe


------------------------------------------------------------------------------
CODE : Protéger une vue classe
------------------------------------------------------------------------------
from django.contrib.auth.mixins import LoginRequiredMixin
from django.views.generic import UpdateView

from .models import Membre


class ProfilUpdateView(LoginRequiredMixin, UpdateView):
    model = Membre
    fields = ["telephone", "adresse"]
    template_name = "catalogue/profil_modifier.html"

    def get_object(self, queryset=None):
        return self.request.user.membre
------------------------------------------------------------------------------


[ATTENTION]

`LoginRequiredMixin` doit être placé à gauche dans l'héritage, avant la vue
générique. L'ordre des classes compte : les méthodes de la première classe
prennent le dessus. Un mixin placé à droite peut être ignoré.

[/ATTENTION]



## Les sessions

Une session associe un identifiant stocké dans un cookie à des données conservées
côté serveur. Django crée la session à la connexion.


------------------------------------------------------------------------------
CODE : Manipuler la session
------------------------------------------------------------------------------
request.session["derniere_recherche"] = "prince"
request.session.get("derniere_recherche")
request.session.set_expiry(60 * 60 * 24 * 7)   # 7 jours
request.session.flush()                        # tout effacer
------------------------------------------------------------------------------


Réglage | Effet
`SESSION_COOKIE_AGE` | Durée de vie en secondes. `1209600` par défaut,
soit deux semaines.
`SESSION_EXPIRE_AT_BROWSER_CLOSE` | Ferme la session à la fermeture du
navigateur.
`SESSION_COOKIE_SECURE` | Cookie uniquement en HTTPS. À activer en
production.
`SESSION_COOKIE_HTTPONLY` | Interdit l'accès au cookie en JavaScript.
Activé par défaut.
`SESSION_SAVE_EVERY_REQUEST` | Écrit la session à chaque requête. Coûteux,
à laisser à `False`.

Tableau : Les réglages de session les plus utiles.


[BONNE PRATIQUE]

En production, activez `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`
et `SECURE_SSL_REDIRECT`. Ces réglages empêchent l'envoi des cookies en
clair sur une connexion HTTP.

[/BONNE PRATIQUE]



## Les validateurs de mot de passe

Django applique quatre validateurs par défaut :


------------------------------------------------------------------------------
CODE : gesibiblio/settings.py, extrait
------------------------------------------------------------------------------
AUTH_PASSWORD_VALIDATORS = [
    {
        "NAME": (
            "django.contrib.auth.password_validation"
            ".UserAttributeSimilarityValidator"
        ),
    },
    {
        "NAME": (
            "django.contrib.auth.password_validation"
            ".MinimumLengthValidator"
        ),
        "OPTIONS": {"min_length": 9},
    },
    {
        "NAME": (
            "django.contrib.auth.password_validation"
            ".CommonPasswordValidator"
        ),
    },
    {
        "NAME": (
            "django.contrib.auth.password_validation"
            ".NumericPasswordValidator"
        ),
    },
]
------------------------------------------------------------------------------


  - `UserAttributeSimilarityValidator` : Refuse un mot de passe trop proche
    du nom ou de l'adresse.
  - `MinimumLengthValidator` : Impose une longueur minimale. Neuf
    caractères est un plancher raisonnable.
  - `CommonPasswordValidator` : Refuse les mots de passe présents dans une
    liste de plusieurs milliers de valeurs courantes.
  - `NumericPasswordValidator` : Refuse un mot de passe uniquement
    numérique.


[NOTE]

Une longueur minimale de neuf caractères protège mieux qu'une exigence de symboles
compliqués, que les utilisateurs contournent en ajoutant `!` à la fin. Les
phrases de passe longues sont préférables.

[/NOTE]



## Réinitialiser un mot de passe

Les vues sont déjà disponibles. Il faut fournir les gabarits et configurer l'envoi
de courrier.


------------------------------------------------------------------------------
CODE : gesibiblio/settings.py, extrait
------------------------------------------------------------------------------
EMAIL_BACKEND = "django.core.mail.backends.console.EmailBackend"
DEFAULT_FROM_EMAIL = "GesiBiblio <noreply@gesibiblio.example>"
------------------------------------------------------------------------------

En développement, `console.EmailBackend` affiche le courrier dans le terminal.
En production, configurez un vrai serveur SMTP.


------------------------------------------------------------------------------
CODE : templates/registration/password_reset_form.html
------------------------------------------------------------------------------
{% extends "base.html" %}

{% block titre %}Mot de passe oublié | GesiBiblio{% endblock %}

{% block contenu %}
  <h1>Mot de passe oublié</h1>
  <p>Saisissez votre adresse électronique. Un lien vous sera envoyé.</p>

  <form method="post" class="formulaire">
    {% csrf_token %}
    {{ form.as_p }}
    <button class="bouton bouton-principal" type="submit">
      Envoyer le lien
    </button>
  </form>
{% endblock %}
------------------------------------------------------------------------------


[ATTENTION]

La page de demande ne doit pas révéler si l'adresse existe. Django affiche le même
message dans les deux cas. C'est volontaire : cela évite l'énumération des comptes.

[/ATTENTION]



## Exercices


============================================================
EXERCICE : page profil protégée
============================================================

Vérifiez qu'un visiteur non connecté qui demande `/comptes/profil/` est
redirigé vers la page de connexion, puis revient au profil après connexion.


[CORRECTION]

Ajoutez la route et le décorateur :


------------------------------------------------------------------------------
CODE : catalogue/urls.py, extrait
------------------------------------------------------------------------------
path("comptes/profil/", views.profil, name="profil"),
------------------------------------------------------------------------------


------------------------------------------------------------------------------
CODE : catalogue/views.py, extrait
------------------------------------------------------------------------------
@login_required
def profil(request):
    ...
------------------------------------------------------------------------------

Avec `LOGIN_URL = "login"`, la redirection est
`/comptes/login/?next=/comptes/profil/`. Le gabarit de connexion doit contenir
{<input type="hidden" name="next" value="{{ next }}">}.

[/CORRECTION]


============================================================
EXERCICE : modification du profil
============================================================

Ajoutez une page qui permet de modifier le téléphone et l'adresse du membre
connecté. Utilisez un `ModelForm` limité à ces deux champs.


[CORRECTION]


------------------------------------------------------------------------------
CODE : catalogue/forms.py, extrait
------------------------------------------------------------------------------
class ProfilForm(forms.ModelForm):
    class Meta:
        model = Membre
        fields = ["telephone", "adresse"]
------------------------------------------------------------------------------


------------------------------------------------------------------------------
CODE : catalogue/views.py, extrait
------------------------------------------------------------------------------
@login_required
def profil_modifier(request):
    membre = request.user.membre

    if request.method == "POST":
        form = ProfilForm(request.POST, instance=membre)
        if form.is_valid():
            form.save()
            messages.success(request, "Votre profil a été mis à jour.")
            return redirect("catalogue:profil")
    else:
        form = ProfilForm(instance=membre)

    return render(
        request,
        "catalogue/profil_modifier.html",
        {"form": form},
    )
------------------------------------------------------------------------------


[NOTE]

Ne demandez jamais le champ `user` dans le formulaire. Un utilisateur pourrait
changer le propriétaire du profil. Le formulaire est limité aux champs qu'il a le
droit de modifier.

[/NOTE]


[/CORRECTION]


============================================================
EXERCICE : compteur de connexions
============================================================

Affichez sur le profil la date de la dernière connexion et le nombre total de
connexions. Utilisez `user.last_login` et le signal `user_logged_in`
pour incrémenter un compteur dans le profil.


[CORRECTION]


------------------------------------------------------------------------------
CODE : catalogue/models.py, extrait
------------------------------------------------------------------------------
class Membre(models.Model):
    # ... champs existants
    nombre_connexions = models.PositiveIntegerField(default=0)
------------------------------------------------------------------------------


------------------------------------------------------------------------------
CODE : catalogue/signals.py
------------------------------------------------------------------------------
from django.contrib.auth.signals import user_logged_in
from django.dispatch import receiver


@receiver(user_logged_in)
def compter_connexion(sender, request, user, **kwargs):
    if hasattr(user, "membre"):
        user.membre.nombre_connexions += 1
        user.membre.save(update_fields=["nombre_connexions"])
------------------------------------------------------------------------------

Branchez le module dans `CatalogueConfig.ready()` :


------------------------------------------------------------------------------
CODE : catalogue/apps.py
------------------------------------------------------------------------------
class CatalogueConfig(AppConfig):
    # ... champs existants

    def ready(self):
        from . import signals  # noqa: F401
------------------------------------------------------------------------------


[NOTE]

Le signal s'exécute à chaque connexion. Utilisez `update_fields` pour ne
écrire qu'une colonne. `hasattr` évite une erreur pour un superutilisateur
sans profil.

[/NOTE]


[/CORRECTION]


[A RETENIR]


  - `django.contrib.auth` fournit les utilisateurs, les sessions et les
    permissions.
  - `include("django.contrib.auth.urls")` active les vues standards.
  - Les gabarits vont dans `registration/`.
  - `login_required` protège une vue fonction ;
    `LoginRequiredMixin` protège une classe.
  - `next` ramène l'utilisateur à la page demandée.
  - La déconnexion se fait en `POST` depuis Django 5.
  - Les mots de passe sont hachés et validés par des validateurs.


[/A RETENIR]



==============================================================================
CHAPITRE 12 : LES PERMISSIONS ET LA SÉCURITÉ
==============================================================================


Un site de bibliothèque accueille des publics différents : les lecteurs consultent et empruntent, les bibliothécaires gèrent le catalogue, les administrateurs configurent le site. Dans ce chapitre, vous mettez en place des groupes, des permissions et des contrôles d'accès. Vous découvrez aussi les réglages de sécurité que tout projet Django doit activer avant la mise en ligne.


OBJECTIFS DU CHAPITRE


  - Comprendre les permissions automatiques créées par Django.
  - Créer des groupes et leur attribuer des droits.
  - Vérifier une permission dans une vue fonction et une vue classe.
  - Afficher ou masquer un élément avec `perms` dans un gabarit.
  - Déclarer une permission personnalisée.
  - Distinguer permission globale et permission objet.
  - Appliquer les réglages de sécurité essentiels.
  - Éviter les erreurs classiques de contrôle d'accès.



## Pourquoi des permissions ?

L'authentification répond à la question « qui êtes-vous ? ». L'autorisation
répond à « avez-vous le droit de faire ceci ? ». Un utilisateur connecté n'est
pas forcément autorisé à supprimer un livre.


[A RETENIR]

Une permission est un droit nommé, par exemple `catalogue.add_livre`. Django
crée automatiquement quatre permissions pour chaque modèle : ajouter, modifier,
supprimer et voir. Les groupes rassemblent des permissions pour les attribuer
facilement à plusieurs utilisateurs.

[/A RETENIR]


[FIGURE] Les utilisateurs reçoivent des groupes ; les groupes portent des permissions ; le contrôle s'effectue dans la vue et dans le gabarit.




## Les permissions automatiques

Pour chaque modèle, Django crée quatre permissions :


Codename | Modèle | Droit
`add_livre` | Livre | Ajouter un livre.
`change_livre` | Livre | Modifier un livre.
`delete_livre` | Livre | Supprimer un livre.
`view_livre` | Livre | Consulter un livre.

Tableau : Les quatre permissions créées pour le modèle Livre.

Le nom complet d'une permission combine l'application et le nom court de
l'action, par exemple `catalogue.change_livre`. Les permissions sont
créées lors de `migrate`, puis mises à jour à chaque migration.


------------------------------------------------------------------------------
CODE : Lire les permissions d'un utilisateur
------------------------------------------------------------------------------
user.has_perm("catalogue.add_livre")
user.has_perm("catalogue.delete_livre")
user.get_all_permissions()
user.get_group_permissions()
user.is_superuser   # True : toutes les permissions
------------------------------------------------------------------------------


[NOTE]

Un superutilisateur réussit toujours `has_perm`, même sans permission
explicite. Un membre du personnel (`is_staff`) n'a pas automatiquement de
droits sur les modèles : il peut seulement accéder à l'interface
d'administration. Les deux notions sont distinctes.

[/NOTE]



## Créer des groupes

Les groupes se gèrent dans l'administration, section « Groupes ». Pour
GesiBiblio, nous créons deux groupes :


Groupe | Permissions
`Lecteurs` | `view_livre`, `view_auteur`,
`view_categorie`, `add_emprunt`, `view_emprunt`
`Bibliothécaires` | Toutes les permissions du catalogue, sauf la suppression
des emprunts.

Tableau : Groupes proposés pour GesiBiblio.


[BONNE PRATIQUE]

Attribuez les permissions aux groupes, pas aux utilisateurs un par un. Quand un
nouveau bibliothécaire arrive, il suffit de l'ajouter au groupe. Quand une
permission change, tous les membres du groupe en bénéficient immédiatement.

[/BONNE PRATIQUE]

On peut aussi créer les groupes par script, dans une migration de données ou une
commande de gestion. Voici une commande simple :


------------------------------------------------------------------------------
CODE : catalogue/management/commands/creer_groupes.py
------------------------------------------------------------------------------
from django.contrib.auth.models import Group, Permission
from django.core.management.base import BaseCommand


class Command(BaseCommand):
    help = "Crée les groupes et permissions de GesiBiblio."

    def handle(self, *args, **options):
        lecteurs, _ = Group.objects.get_or_create(name="Lecteurs")
        bibliothecaires, _ = Group.objects.get_or_create(
            name="Bibliothécaires"
        )

        codes_lecteurs = [
            "view_livre",
            "view_auteur",
            "view_categorie",
            "add_emprunt",
            "view_emprunt",
        ]
        codes_biblio = [
            "add_livre",
            "change_livre",
            "delete_livre",
            "view_livre",
            "add_auteur",
            "change_auteur",
            "add_categorie",
            "change_categorie",
            "view_emprunt",
            "change_emprunt",
            "view_membre",
        ]

        lecteurs.permissions.set(
            Permission.objects.filter(
                content_type__app_label="catalogue",
                codename__in=codes_lecteurs,
            )
        )
        bibliothecaires.permissions.set(
            Permission.objects.filter(
                content_type__app_label="catalogue",
                codename__in=codes_biblio,
            )
        )

        self.stdout.write(self.style.SUCCESS("Groupes créés."))
------------------------------------------------------------------------------


TERMINAL :
  $ python manage.py creer_groupes


[ATTENTION]

Le dossier `management/commands/` doit contenir des fichiers
`__init__.py` à chaque niveau. Sans eux, Django ne découvre pas la
commande et affiche `Unknown command`.

[/ATTENTION]



## Vérifier une permission dans une vue



### Le décorateur permission_required


------------------------------------------------------------------------------
CODE : Protéger une vue fonction
------------------------------------------------------------------------------
from django.contrib.auth.decorators import (
    login_required,
    permission_required,
)


@login_required
@permission_required("catalogue.add_livre", raise_exception=True)
def livre_creer(request):
    ...
------------------------------------------------------------------------------


  - `login_required` : Redirige un visiteur non connecté vers la
    connexion.
  - `permission_required` : Vérifie la permission. Sans
    `raise_exception`, l'utilisateur connecté mais non autorisé est redirigé
    vers la connexion, ce qui est déroutant.
  - `raise_exception=True` : Renvoie une erreur `403 Forbidden`,
    plus correcte pour un utilisateur authentifié.


[ATTENTION]

L'ordre des décorateurs compte. Placez `login_required` au-dessus de
`permission_required` pour que le visiteur soit d'abord authentifié. Dans
tous les cas, utilisez `raise_exception=True` : un utilisateur connecté sans
droit doit recevoir une 403, pas une page de connexion.

[/ATTENTION]



### Le mixin PermissionRequiredMixin


------------------------------------------------------------------------------
CODE : Protéger une vue classe
------------------------------------------------------------------------------
from django.contrib.auth.mixins import (
    LoginRequiredMixin,
    PermissionRequiredMixin,
)
from django.views.generic import CreateView

from .forms import LivreForm
from .models import Livre


class LivreCreateView(
    LoginRequiredMixin,
    PermissionRequiredMixin,
    CreateView,
):
    model = Livre
    form_class = LivreForm
    template_name = "catalogue/livres/formulaire.html"
    permission_required = "catalogue.add_livre"
    raise_exception = True
------------------------------------------------------------------------------


[ATTENTION]

L'ordre d'héritage est important : `LoginRequiredMixin` puis
`PermissionRequiredMixin` puis la vue générique. Si vous inversez, le contrôle
peut être court-circuité. `permission_required` accepte aussi une liste de
permissions, auquel cas toutes sont exigées.

[/ATTENTION]



## Les permissions dans les gabarits

Le processeur de contexte `auth` expose `perms`. On peut ainsi masquer un
bouton que l'utilisateur ne peut pas utiliser.


------------------------------------------------------------------------------
CODE : Afficher selon les droits
------------------------------------------------------------------------------
{% if perms.catalogue.add_livre %}
  <a class="bouton bouton-principal"
     href="{% url 'catalogue:livre_creer' %}">Ajouter un livre</a>
{% endif %}

{% if perms.catalogue.change_livre %}
  <a class="bouton"
     href="{% url 'catalogue:livre_modifier' livre.slug %}">Modifier</a>
{% endif %}

{% if perms.catalogue.delete_livre %}
  <a class="bouton bouton-danger"
     href="{% url 'catalogue:livre_supprimer' livre.slug %}">Supprimer</a>
{% endif %}
------------------------------------------------------------------------------


[ATTENTION]

Masquer un bouton dans le gabarit ne protège rien. Un utilisateur peut saisir
l'URL directement. La vérification du gabarit améliore l'expérience ; la vraie
protection est dans la vue. Faites toujours les deux.

[/ATTENTION]


[BONNE PRATIQUE]

Le nom dans le gabarit suit la forme `perms.<application>.<codename>`. Ici,
`perms.catalogue.add_livre`. Vérifiez l'orthographe exacte dans
l'administration, section permissions : une faute de frappe masque silencieusement
le bouton, sans provoquer d'erreur.

[/BONNE PRATIQUE]



## Une permission personnalisée

Les quatre permissions automatiques ne suffisent pas toujours. Par exemple,
« valider un emprunt » ou « exporter le catalogue » sont des actions
propres au métier.


------------------------------------------------------------------------------
CODE : catalogue/models.py, extrait
------------------------------------------------------------------------------
class Livre(models.Model):
    # ... champs existants

    class Meta:
        # ... options existantes
        permissions = [
            ("peut_marquer_perdu", "Peut marquer un livre comme perdu"),
            ("peut_exporter_catalogue", "Peut exporter le catalogue"),
        ]
------------------------------------------------------------------------------

Après `makemigrations` et `migrate`, les permissions apparaissent dans
l'administration. On les vérifie ainsi :


------------------------------------------------------------------------------
CODE : Vérifier une permission personnalisée
------------------------------------------------------------------------------
@permission_required(
    "catalogue.peut_marquer_perdu",
    raise_exception=True,
)
@require_POST
def livre_marquer_perdu(request, slug):
    livre = get_object_or_404(Livre, slug=slug)
    livre.statut = Livre.Statut.PERDU
    livre.save(update_fields=["statut"])
    messages.warning(request, "Le livre a été marqué comme perdu.")
    return redirect(livre)
------------------------------------------------------------------------------


[NOTE]

Une permission personnalisée n'a pas de comportement automatique. Elle sert
uniquement de drapeau que vous vérifiez dans vos vues. C'est vous qui décidez ce
qu'elle autorise.

[/NOTE]



## Permissions objet

Les permissions globales disent « peut modifier un livre ». Les permissions
objet disent « peut modifier ce livre précis ». Django ne les fournit pas
automatiquement : il faut les implémenter.


------------------------------------------------------------------------------
CODE : Vérification objet
------------------------------------------------------------------------------
if request.user.has_perm("catalogue.change_livre", livre):
    ...
------------------------------------------------------------------------------

Pour un projet de bibliothèque, cette finesse est rarement nécessaire. En revanche,
elle est utile pour un blog multi-auteurs ou un espace client. Une implémentation
simple consiste à comparer le propriétaire :


------------------------------------------------------------------------------
CODE : Contrôle manuel du propriétaire
------------------------------------------------------------------------------
def livre_modifier(request, slug):
    livre = get_object_or_404(Livre, slug=slug)

    if livre.cree_par_id != request.user.id and not request.user.has_perm(
        "catalogue.change_livre"
    ):
        raise PermissionDenied

    ...
------------------------------------------------------------------------------


[ATTENTION]

`PermissionDenied` produit une réponse `403`. N'utilisez pas une
redirection silencieuse : l'utilisateur doit comprendre qu'il n'a pas le droit.
Journalisez l'événement si l'action est sensible.

[/ATTENTION]



## Les réglages de sécurité

Avant une mise en ligne, parcourez cette liste. Django fournit d'ailleurs une
commande de vérification.


TERMINAL :
  $ python manage.py check --deploy


------------------------------------------------------------------------------
CODE : gesibiblio/settings.py, extraits de production
------------------------------------------------------------------------------
DEBUG = False

ALLOWED_HOSTS = ["bibliotheque.example", "www.bibliotheque.example"]

SECURE_SSL_REDIRECT = True
SESSION_COOKIE_SECURE = True

`ALLOWED_HOSTS` | Liste blanche des noms de domaine acceptés.

`CSRF_COOKIE_SECURE` | Cookie CSRF uniquement en HTTPS.
`SECURE_HSTS_SECONDS` | Impose HTTPS au navigateur pendant un an.
`X_FRAME_OPTIONS` | Empêche l'affichage dans une iframe, contre le
clickjacking.
`SECURE_CONTENT_TYPE_NOSNIFF` | Empêche la devinette du type de contenu.

Tableau : Les réglages de sécurité à activer en production.


[ATTENTION]

Activez HSTS avec prudence. Une fois envoyé, l'en-tête demande au navigateur
d'utiliser HTTPS pendant la durée indiquée, même si votre certificat tombe. Testez
d'abord avec une durée courte, puis augmentez.

[/ATTENTION]



### Les secrets


------------------------------------------------------------------------------
CODE : Lire un secret depuis l'environnement
------------------------------------------------------------------------------
import os

SECRET_KEY = os.environ["DJANGO_SECRET_KEY"]
------------------------------------------------------------------------------


[BONNE PRATIQUE]

La `SECRET_KEY` ne doit jamais figurer dans un dépôt public. Utilisez une
variable d'environnement, un fichier `.env` non versionné ou un coffre de
secrets. Générez une clé longue et aléatoire, différente pour chaque
environnement.

[/BONNE PRATIQUE]


[ERREUR FREQUENTE]

Changer la `SECRET_KEY` invalide les sessions, les jetons de réinitialisation
et les signatures existantes. C'est normal, mais prévenez les utilisateurs si vous
le faites en production.

[/ERREUR FREQUENTE]



## Les erreurs classiques de contrôle d'accès


  1. Masquer sans protéger. Cacher un bouton ne bloque pas l'URL.
  2. Oublier `raise_exception`. L'utilisateur connecté sans droit
    est renvoyé vers la connexion, ce qui masque le vrai problème.
  3. Confondre `is_staff` et permissions. Un membre du personnel
    peut entrer dans l'administration sans pouvoir modifier vos modèles.
  4. Faire confiance à un identifiant dans le formulaire. Un champ
    caché `user_id` peut être modifié. Prenez l'utilisateur dans
    `request.user`.
  5. Utiliser `GET` pour modifier. Une image ou un lien peut
    déclencher l'action.
  6. Laisser `DEBUG = True`. Les pages d'erreur révèlent le code,
    les chemins et les réglages.


------------------------------------------------------------------------------
CODE : Un formulaire ne décide pas du propriétaire
------------------------------------------------------------------------------
# Mauvais : le client choisit le propriétaire.
livre.cree_par_id = request.POST.get("user_id")

# Bon : le serveur impose l'utilisateur connecté.
livre.cree_par = request.user
------------------------------------------------------------------------------


[BONNE PRATIQUE]

Principe du moindre privilège : donnez le droit minimal nécessaire. Un lecteur n'a
pas besoin de modifier le catalogue. Un bibliothécaire n'a pas besoin de gérer les
utilisateurs. Un administrateur technique n'a pas besoin de modifier les emprunts.

[/BONNE PRATIQUE]

============================================================
EXERCICE : réserver un livre
============================================================

Ajoutez une vue `livre_reserver` protégée par la permission
`catalogue.add_emprunt`. La vue crée un emprunt pour l'utilisateur connecté,
avec une date de retour prévue dans quatorze jours. Refusez si le livre n'est pas
disponible.


[CORRECTION]


------------------------------------------------------------------------------
CODE : catalogue/views.py, extrait
------------------------------------------------------------------------------
from datetime import timedelta

from django.contrib.auth.decorators import (
    login_required,
    permission_required,
)
from django.utils import timezone
from django.views.decorators.http import require_POST


@login_required
@permission_required("catalogue.add_emprunt", raise_exception=True)
@require_POST
def livre_reserver(request, slug):
    livre = get_object_or_404(Livre, slug=slug)

    if not livre.est_disponible:
        messages.error(request, "Ce livre n'est pas disponible.")
        return redirect(livre)

    Emprunt.objects.create(
        livre=livre,
        membre=request.user.membre,
        date_retour_prevue=timezone.localdate() + timedelta(days=14),
    )
    messages.success(request, "Votre réservation est enregistrée.")
    return redirect("catalogue:profil")
------------------------------------------------------------------------------


[NOTE]

La permission `add_emprunt` ne garantit pas que le membre possède un profil.
Vérifiez `hasattr(request.user, "membre")` ou créez le profil à l'inscription
comme au chapitre précédent.

[/NOTE]


[/CORRECTION]

EXERCICE : audit des droits
============================================================

Écrivez une commande `audit_droits` qui affiche, pour chaque groupe, la liste
des permissions triées. Utilisez `group.permissions.all()`.


[CORRECTION]


------------------------------------------------------------------------------
CODE : catalogue/management/commands/audit_droits.py
------------------------------------------------------------------------------
from django.contrib.auth.models import Group
from django.core.management.base import BaseCommand


class Command(BaseCommand):
    help = "Affiche les permissions de chaque groupe."

    def handle(self, *args, **options):
        for groupe in Group.objects.prefetch_related("permissions"):
            self.stdout.write(self.style.MIGRATE_HEADING(groupe.name))
            for permission in groupe.permissions.all():
                libelle = (
                    f"{permission.content_type.app_label}."
                    f"{permission.codename}"
                )
                self.stdout.write(f"  - {libelle}")
------------------------------------------------------------------------------

Lancez `python manage.py audit_droits`. Cette commande est utile avant une
mise en production pour vérifier qu'aucun groupe ne possède de droit excessif.

[/CORRECTION]


[A RETENIR]


  - Django crée quatre permissions par modèle : add, change, delete, view.
  - Les groupes simplifient l'attribution des droits.
  - `permission_required` et `PermissionRequiredMixin` protègent les
    vues.
  - `perms` dans les gabarits améliore l'affichage, pas la sécurité.
  - Une permission personnalisée est un drapeau vérifié par votre code.
  - `DEBUG = False`, HTTPS, cookies sécurisés et `ALLOWED_HOSTS`
    sont indispensables en production.
  - Le moindre privilège limite les dégâts en cas de compromission.


[/A RETENIR]

## Écrire des tests

Les tests automatisés vérifient qu'une page répond, qu'un formulaire refuse une
donnée invalide, qu'un utilisateur sans permission reçoit une 403. Django fournit
un client de test et une base de test isolée.


------------------------------------------------------------------------------
CODE : catalogue/tests.py
------------------------------------------------------------------------------
from django.contrib.auth.models import User
from django.test import TestCase
from django.urls import reverse

from .models import Auteur, Livre


class CatalogueTests(TestCase):

## Glossaire


  - Application : Module Django qui remplit une responsabilité, par exemple
    `catalogue`.
  - Cadriciel (framework) : Ensemble d'outils et de conventions qui structurent
    une application.
  - CSRF : Attaque qui force un utilisateur connecté à envoyer une requête non
    désirée. Django la bloque avec un jeton.
  - Gabarit (template) : Fichier HTML contenant des balises Django.
  - Migration : Fichier qui décrit une évolution du schéma de base de données.
  - MVT : Modèle, Vue, Gabarit : l'organisation des responsabilités dans
    Django.
  - ORM : Couche qui traduit les objets Python en requêtes SQL.
  - Permission : Droit nommé, par exemple `add_livre`.
  - QuerySet : Ensemble de résultats d'une requête ORM, paresseux et
    chaînable.
  - Slug : Version d'une chaîne utilisable dans une URL.
  - Superutilisateur : Compte qui possède tous les droits.
  - Vue : Fonction ou classe qui reçoit une requête et renvoie une réponse.
  - XSS : Injection de script dans une page. Django échappe le HTML par défaut.

==============================================================================
ANNEXE C : ERREURS FRÉQUENTES ET SOLUTIONS
==============================================================================


Cette annexe classe les erreurs que l'on rencontre le plus souvent en apprenant Django. Pour chacune, elle donne le message typique, la cause probable et la correction. Lisez toujours le message complet : Django indique presque toujours le fichier et la ligne.



## Lire un message d'erreur

Un message Django contient généralement :

  1. le type d'exception, par exemple `TemplateDoesNotExist` ;
  2. la valeur ou le nom concerné ;
  3. la liste des chemins essayés, pour les gabarits ;
  4. la trace complète, avec les fichiers et les lignes.


[BONNE PRATIQUE]

Lisez la dernière ligne d'abord, puis remontez la trace. La dernière ligne donne
l'exception ; la première ligne de votre code dans la trace indique souvent
l'endroit à corriger. Ne copiez pas tout le message dans un moteur de recherche :
cherchez d'abord le type d'exception et le nom du fichier.

[/BONNE PRATIQUE]



## Erreurs de projet et de configuration


Message | Cause | Correction
`ModuleNotFoundError` | Django absent de l'environnement virtuel
ou environnement inactif. | Activez `.venv`, puis
`pip install Django`.
`No installed app` | Le label `catalogue` est inconnu :
application absente de `INSTALLED_APPS`. | Ajoutez
`"catalogue"` dans les réglages, ou `CatalogueConfig`
dans `apps.py`.
`ModuleNotFoundError` | Le paquet `catalogue` est
introuvable : dossier mal placé ou `__init__.py` absent. | Vérifiez l'arborescence et le fichier
`__init__.py`.
`ImproperlyConfigured` | Clé `SECRET_KEY` absente ou vide. | Définissez
`SECRET_KEY` dans `settings.py` ou l'environnement.
`DisallowedHost` | Domaine absent de `ALLOWED_HOSTS`. | Ajoutez le
domaine, ou `localhost` et `127.0.0.1` en développement.
Port déjà utilisé | Un serveur tourne déjà. | Utilisez
`runserver 8001` ou arrêtez l'autre processus.
`ImportError` | Import circulaire ou nom `X` inexistant. |
Déplacez l'import dans une fonction, ou corrigez le nom.



## Erreurs d'URL et de vue


Message | Cause | Correction
`NoReverseMatch` | Nom de route inconnu ou argument manquant. | Vérifiez
`app_name`, le `name` de la route et les paramètres.
`Page not found (404)` | Aucune route ne correspond. | Vérifiez l'ordre des
`path` et le slash final.
`TypeError` | Une classe de vue est passée sans
`.as_view()`. | Ajoutez `.as_view()`.
`AttributeError` | `include` pointe vers un module sans
`urlpatterns`. | Créez `urls.py` avec
`urlpatterns`.
`404` sur un slug valide | Le convertisseur ne correspond pas. | Utilisez
`<slug:slug>` et vérifiez la valeur en base.
`405 Method Not Allowed` | Vue limitée à `GET` ou `POST`. |
Adaptez le décorateur ou envoyez la bonne méthode.
`CSRF verification failed` | Jeton absent ou cookie bloqué
(erreur 403). | Ajoutez
`{% csrf_token %}` et vérifiez les cookies.



## Erreurs de gabarit


Message | Cause | Correction
`TemplateDoesNotExist` | Chemin incorrect ou dossier absent de
`DIRS`. | Vérifiez `TEMPLATES` et le chemin exact.
`Invalid block tag` | Balise mal orthographiée ou non chargée. | Vérifiez
l'orthographe et ajoutez `{% load ... %}`.
`Invalid filter` | Filtre inconnu ou bibliothèque non chargée. | Chargez
`templatetags` avec `{% load biblio %}`.
`TemplateSyntaxError` | Balise non fermée, par exemple
`{% if %}` sans `{% endif %}`. | Fermez chaque bloc.
`VariableDoesNotExist` | Variable absente du contexte. | Vérifiez la clé
passée par la vue.
`NoReverseMatch` dans un gabarit | URL mal formée. | Corrigez le nom ou
l'argument de `{% url %}`.
Page vide à l'endroit attendu | Nom de variable incorrect. | Comparez le contexte
de la vue et le gabarit.



## Erreurs de modèle et de base


Message | Cause | Correction
`no such table` | Migrations non appliquées. | Lancez `migrate`.
`no such column` | Modèle modifié sans migration. | Lancez
`makemigrations` puis `migrate`.
`NOT NULL constraint failed` | Champ obligatoire laissé vide. | Fournissez
une valeur ou autorisez `null`/`blank`.
`UNIQUE constraint failed` | Doublon sur un champ unique. | Vérifiez
l'existence avant `create`, ou gérez l'erreur.
`IntegrityError` | Clé étrangère invalide (contrainte
`FOREIGN KEY`). |
Vérifiez que l'objet lié existe.
`ProtectedError` | Suppression bloquée par `PROTECT`. | Supprimez
d'abord les objets liés, ou utilisez un autre comportement.
`DoesNotExist` | `get()` ne trouve rien. | Utilisez
`get_object_or_404` dans une vue.
`MultipleObjectsReturned` | `get()` trouve plusieurs objets. | Filtrez
sur un champ unique.
`RelatedObjectDoesNotExist` | Profil un à un absent. | Créez le profil, ou
testez `hasattr`.



## Erreurs de formulaire et de fichier


Message | Cause | Correction
Formulaire toujours invalide | Champ obligatoire vide ou erreur masquée. |
Affichez `form.errors` et vérifiez `cleaned_data`.
`This field is required` | Champ non rempli. | Rendez-le facultatif avec
`required=False` ou corrigez la saisie.
Fichier non enregistré | `enctype` absent ou `request.FILES` oublié. |
Ajoutez `multipart/form-data` et le second argument.
`Upload a valid image` | Fichier corrompu ou Pillow absent. | Vérifiez
l'image et installez Pillow.
`KeyError: 'champ'` dans `clean()` | Champ déjà invalide. | Utilisez
`cleaned_data.get`.
`ValueError` | Conversion d'une chaîne non numérique en entier. | Testez `isdigit()` ou utilisez un formulaire.



## Erreurs de permission et d'authentification


Message | Cause | Correction
Redirection infinie vers login | `LOGIN_URL` pointe vers une vue protégée. |
Vérifiez la route de connexion.
`403 Forbidden` après connexion | Permission absente. | Ajoutez la permission
au groupe ou à l'utilisateur.
`405` à la déconnexion | Lien au lieu d'un formulaire `POST`. | Utilisez
un formulaire avec `csrf_token`.
`RelatedObjectDoesNotExist` | Profil membre absent pour
`user` (relation un à un). | Créez le profil
à l'inscription, ou testez `hasattr`.
Session perdue au redémarrage | `SECRET_KEY` change ou base vidée. |
Stabilisez la clé et conservez la base.
Identifiants refusés | Nom d'utilisateur ou mot de passe invalide, ou
compte inactif. | Vérifiez `is_active` et le mot de passe.



## Erreurs de fichiers statiques


Message | Cause | Correction
CSS non chargé en développement | `STATICFILES_DIRS` incorrect ou
`{% load static %}` absent. | Vérifiez le chemin et la balise.
`404` sur `/static/` | Fichier absent ou `DEBUG = False`. |
Vérifiez le fichier, ou lancez `--insecure` pour tester.
CSS non chargé en production | `collectstatic` non exécuté ou Nginx mal
configuré. | Lancez `collectstatic` et vérifiez l'`alias`.
Image média inaccessible | `MEDIA_URL` ou `MEDIA_ROOT` incorrect. |
Vérifiez les deux réglages et l'URL `static()`.
Ancien CSS affiché | Cache du navigateur. | Videz le cache ou utilisez un nom
hashé.



## Erreurs de déploiement


Message | Cause | Correction
`500` en production, rien en local | `DEBUG = False` masque la trace. |
Consultez les journaux du serveur.
`Bad Request (400)` | `ALLOWED_HOSTS` incomplet. | Ajoutez le domaine
exact, sans `https://`.
Fichiers statiques absents | `collectstatic` oublié. | Lancez la commande et
vérifiez `STATIC_ROOT`.
`CSRF` échoue derrière un proxy | En-tête `X-Forwarded-Proto` non
transmis. | Configurez Nginx et `SECURE_PROXY_SSL_HEADER`.
Connexion impossible à PostgreSQL | Identifiants ou service arrêté. | Vérifiez
`DATABASES` et l'état du service.
`Too many connections` | Fuite de connexions ou trafic élevé. | Utilisez le
pooling et surveillez la base.


[ERREUR FREQUENTE]

Ne corrigez jamais une erreur en désactivant une protection : `CSRF_COOKIE_SECURE`,
`ALLOWED_HOSTS`, les permissions ou `DEBUG`. Cherchez la cause réelle.
Une protection désactivée pour « faire marcher » devient une faille en
production.

[/ERREUR FREQUENTE]



## Méthode de débogage


  1. Reproduire l'erreur de façon fiable.
  2. Lire le type d'exception et la dernière ligne de la trace.
  3. Vérifier la configuration : application installée, URL incluse, gabarit
    présent, migration appliquée.
  4. Ajouter un `print` ou un `breakpoint()` dans la vue pour voir
    les valeurs.
  5. Utiliser le shell Django pour tester la requête ORM isolément.
  6. Réduire le problème à un cas minimal.
  7. Écrire un test qui reproduit le bug, puis corriger.

class Command(BaseCommand):
    help = "Crée un jeu de données de démonstration pour GesiBiblio."

    def add_arguments(self, parser):
        parser.add_argument(
            "--reset",
            action="store_true",
            help="Supprime les emprunts et les livres de démonstration.",
        )

    def handle(self, *args, **options):
        if options["reset"]:
            self.reset()

        auteurs = {}
        for prenom, nom, naissance in AUTEURS:
            auteur, _ = Auteur.objects.get_or_create(
                prenom=prenom,
                nom=nom,
                defaults={
                    "date_naissance": date(naissance, 1, 1),
                },
            )
            auteurs[nom] = auteur

        categories = {}
        for nom, slug, description in CATEGORIES:
            categorie, _ = Categorie.objects.get_or_create(
                slug=slug,
                defaults={"nom": nom, "description": description},
            )
            categories[nom] = categorie

        for (
            titre,
            slug,
            isbn,
            prenom,
            nom,
            annee,
            exemplaires,
            noms_categories,
            resume,
        ) in LIVRES:
            livre, cree = Livre.objects.get_or_create(
                slug=slug,
                defaults={
                    "titre": titre,
                    "isbn": isbn,
                    "auteur": auteurs[nom],
                    "annee_publication": annee,
                    "nombre_exemplaires": exemplaires,
                    "resume": resume,
                },
            )
            if cree:
                livre.categories.set(
                    [categories[n] for n in noms_categories]
                )
                self.stdout.write(f"  + {livre.titre}")

        membres = self.creer_membres()
        self.creer_emprunts(membres)

        self.stdout.write(
            self.style.SUCCESS("Données de démonstration prêtes.")
        )

    def creer_membres(self):
        membres = []
        for numero, username, prenom, nom in [
            ("M00001", "lecteur1", "Awa", "Ndiaye"),
            ("M00002", "lecteur2", "Kofi", "Mensah"),
        ]:
            user, cree = User.objects.get_or_create(
                username=username,
                defaults={
                    "first_name": prenom,
                    "last_name": nom,
                    "email": f"{username}@example.com",
                },
            )
            if cree:
                user.set_password("Demonstration2026!")
                user.save()

            membre, _ = Membre.objects.get_or_create(
                user=user,
                defaults={"numero": numero},
            )
            membres.append(membre)

        lecteurs, _ = Group.objects.get_or_create(name="Lecteurs")
        for membre in membres:
            membre.user.groups.add(lecteurs)

        return membres

    def creer_emprunts(self, membres):
        aujourdhui = timezone.localdate()
        livre = Livre.objects.filter(slug="le-petit-prince").first()
        if not livre or not membres:
            return

        Emprunt.objects.get_or_create(
            livre=livre,
            membre=membres[0],
            date_emprunt=aujourdhui - timedelta(days=5),
            defaults={
                "date_retour_prevue": aujourdhui + timedelta(days=9),
            },
        )

        livre2 = Livre.objects.filter(slug="l-etranger").first()
        if livre2:
            Emprunt.objects.get_or_create(
                livre=livre2,
                membre=membres[1],
                date_emprunt=aujourdhui - timedelta(days=30),
                defaults={
                    "date_retour_prevue": aujourdhui - timedelta(days=2),
                },
            )

    def reset(self):
        Emprunt.objects.all().delete()
        Livre.objects.filter(
            slug__in=[livre[1] for livre in LIVRES]
        ).delete()
        self.stdout.write("Livres et emprunts de démonstration supprimés.")

et documenté. Ne l'utilisez jamais en production.

[/NOTE]

## Réinitialiser


TERMINAL :
  $ python manage.py donnees_demo --reset
  $ python manage.py donnees_demo


[ATTENTION]

`--reset` supprime les emprunts et les livres dont le slug figure dans la
liste de démonstration. Il ne supprime ni les auteurs, ni les catégories, ni les
membres. Pour repartir de zéro, utilisez une base de développement dédiée :
`python manage.py flush` vide toutes les données, mais conserve le schéma.

[/ATTENTION]



## Alternative : une fixture JSON

Pour un jeu de données figé, Django accepte des fixtures. Créez le fichier
`categories.json` dans un dossier `fixtures/` de l'application :


------------------------------------------------------------------------------
CODE : catalogue/fixtures/categories.json
------------------------------------------------------------------------------
[
  {
    "model": "catalogue.categorie",
    "pk": 1,
    "fields": {
      "nom": "Roman",
      "slug": "roman",
      "description": "Fictions longues et récits."
    }
  },
  {
    "model": "catalogue.categorie",
    "pk": 2,
    "fields": {
      "nom": "Jeunesse",
      "slug": "jeunesse",
      "description": "Albums et romans pour les jeunes."
    }
  }
]
------------------------------------------------------------------------------


TERMINAL :
  $ python manage.py loaddata categories


[NOTE]

La commande `loaddata` cherche le fichier dans les dossiers
`fixtures/` des applications installées. Une fixture est pratique pour des
données de référence stables, moins pour des données qui doivent être recalculées
ou créées avec des mots de passe hachés.

[/NOTE]


[BONNE PRATIQUE]

Pour les données de référence (catégories, langues, pays), une migration de données
ou une commande idempotente est préférable à une fixture. Pour des données de test
figées, la fixture reste simple et lisible.

[/BONNE PRATIQUE]
